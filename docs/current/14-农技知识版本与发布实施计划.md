# 农技知识版本与发布实施计划

版本V1.2，2026-11-10；依据[07客户端设计](07-客户端设计与实施手册.md)与[后台协同](03-后台管理与三端协同设计.md)。本轮工程源码、后台浏览器与共享HTTP链已完成，微信/手机未验。用户指出应使用AI/网上资料减轻老板负担，本模块改为可选的店内经验资料工具，不再作为AI前置。不代表AI或完整C1已交付。下列字段和技术取舍由技术负责人确定，不冒称用户逐项指定。

**目标：**需要沉淀店内经验时，后台保存草稿→人工审核→发布/撤回→客户端按地区、作物、阶段阅读同一有效版本，旧版本可追溯。之后员工或AI引用店内经验须使用这套受控事实；AI也可检索经来源和适用校验的外部资料，不以本模块有文章作为启用前提。

**架构：**单一知识版本表、既有员工/门店权限和操作日志、同Flex事务。没有向量库、多级审批或第二套文章内容。Java17/Spring/JDBC，Vue3与现有uni-app，共享白名单解码。

## 影响与结构必要性

- 新增`agronomy_knowledge_revision`，V148；现有商品说明没有受众、适用范围、审核版本、撤回和引用历史，操作日志不应当作内容存储。直接维护文件可以试稿，但不能满足后台多员工受控审核、并发发布和客户当前版本查询，因此正式发布需要这一个表。无存量知识迁移、不预造文章，不改钱货表。
- 每次保存新增不可改正文的版本，草稿也不原地覆盖；同组第一版作为稳定锁行。logicalKey+revision唯一，同员工requestKey唯一。首次logicalKey沿安全UUID请求号，后续按原组创建新版本，不另建逻辑主表/请求表。
- 表中保留内容/范围/来源及其hash、审核人/时间、发布/撤回时间、状态/version、创建请求身份/摘要。`sys_operation_log`保存真实操作人、组/版本、决定原因，同事务失败回滚，不放原农户隐私。
- 新权限`agronomy:knowledge:query/write/review/publish`随迁移落真实菜单，不自动给角色授权。普通员工只本店，实际启用管理员角色可跨店；写、审核、发布分别叠加query权限。小店老板可审核自己录入的内容，不强制四眼审批。
- 地区/作物/阶段采用经录入核对的短文本，精确匹配，不猜农户位置或农时；暂不建三套字典表。公开筛选选项仅从当前有效公开版本派生，最多200个组合，超限明确拒绝并提示维护，不能静默截断。

## 内容与状态

内容字段：title(200)、summary(500)、crop(50)、region(100)、growthStage(100)、appliesTo(2000)、exclusions(2000)、body(20000)、sourceText(2000)、audience(PUBLIC/INTERNAL)、riskLevel(LOW/REQUIRES_HUMAN)、effectiveFrom/Until(日期)。单位为字符上限，正文仅纯文本；多行字段允许正常换行，拒绝其余控制字符。标题必填；草稿允许其他内容未完善，审核时必须逐项完整并有明确有效期。

- `DRAFT→REVIEWED→PUBLISHED`，任一非撤回版本可`WITHDRAWN`。已撤回版本不能重新发布，需另存新版重新审核。正文和适用范围创建后不可改，审核指向固定hash。
- 同组可有新版草稿/已审核版与一个原发布版；只有新版正式发布时，原发布版在同事务撤回。并发只允许一个当前发布版本。
- 发布版本必须大于该组曾经发布过的最高版本；即使更新版本后来撤回，也不允许迟到的旧审核操作重新公开旧内容。需重新保存并审核新版本。
- 状态使用version作原确认CAS；资料变化或版本冲突拒绝，不自动重发。结果未知先重读当前事实，不把当前状态冒称原请求成功。创建草稿固定UUID和完整摘要，未知沿原请求查询/重放，同号改体拒绝。
- 公开仅PUBLISHED+PUBLIC+LOW、门店启用未删、服务端上海日期在有效期内，并完整匹配地区/作物/阶段。内部或需人工的知识不通过公开接口。此知识有效期是审核适用期限，与库存粗略日期仅提醒的经营规则不同，不改库存销售资格。
- 历史版本保留，公开详情只返回当前有效版；携原revision读取且版本已变化时拒绝，不能把新正文伪装成旧引用。新引用不得命中撤稿/失效/内部/跨适用范围内容。

## 接口合同

ID为正Long字符串，logicalKey/requestKey为标准小写安全UUID；revision为正整数，version为正Long字符串；日期YYYY-MM-DD，审核时间为服务器上海时间ISO文本。列表每页20，游标取第21条判断下一页。正文/hash由服务端计算，不接客户端作者、审核人、状态或店外归属。

| 入口 | 合同 |
|---|---|
| GET `/api/admin/agronomy/knowledge` | after/storeId筛选，真实权限范围的版本列表，按id递减，至多20项 |
| GET `/api/admin/agronomy/knowledge/{logicalKey}/revisions/{revision}` | 原组/原版本详情，核本店 |
| GET `/api/admin/agronomy/knowledge/{logicalKey}/latest` | 当前实际最新版本，只读；另存旧正文前读取真实版本号，不猜最新 |
| GET `/api/admin/agronomy/knowledge/submissions/{requestKey}` | 当前员工原创建请求结果UNKNOWN/CREATED，不借其他员工请求读资料 |
| POST `/api/admin/agronomy/knowledge` | 固定requestKey/storeId/content，首次expectedLatestRevision=0，创建第一版 |
| POST `/api/admin/agronomy/knowledge/{logicalKey}/revisions` | 固定requestKey/content/expectedLatestRevision，锁组后追加新版；重放原请求优先于最新版本检查 |
| POST `/api/admin/agronomy/knowledge/{logicalKey}/revisions/{revision}/{review,publish,withdraw}` | expectedVersion与必填原因；URL确定组/版本，当前员工由后端取；同Flex锁/CAS/审计 |
| GET `/api/public/agronomy/knowledge/scopes` | 当前有效公开的region/crop/growthStage组合，不读内部候选 |
| GET `/api/public/agronomy/knowledge` | region/crop/growthStage必填，after/keyword可选；白名单纯文本摘要 |
| GET `/api/public/agronomy/knowledge/{logicalKey}` | 同三项范围与expectedRevision必填，当前有效公开详情/来源/范围/审核日期；no-store |

公开接口不带登录/临时令牌，后台接口逐次核真实员工/权限；列表与详情SQL先过滤，不先取内部内容再靠前端隐藏。客户不接假问诊、假提交或假AI按钮。

## 审查重点与最终门槛

1. 多行/长标题/正常中文来源，不能一条内容损坏整页；错误/空值与有效零项分开。
2. 同组两个不同已审核版本并发发布，以及发布/撤回/新建的锁序；旧引用不得读到另一正文。
3. 日期边界/上海零点、门店停用、撤权和换店，不能沿旧页面继续公开。
4. 请求丢响应、重放时已有新版本、同员工同UUID不同组/内容；不能重复创建或认错结果。
5. 公开列表/详情/选项一处漏过滤造成内部或范围不适用内容外泄；无向量检索或AI旁路。

老板预先整理20条SOP不再是开发或AI接通门槛；此前征集3—5例仅作可选了解，不等待这些材料才能开发。店内经验如需正式公开仍须老板审核；网络资料走拟联网检索来源/时效/适用与引用校验，不自动变成“门店已审核知识”。真实微信/手机与目标环境验收不由绿测代替。后续主线按07末尾AI纠偏执行，不继续扩建文章运营系统。
