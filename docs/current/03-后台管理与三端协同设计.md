## 2. 三端职责

| 对象 | 后台管理端 | 员工手机 | 客户手机 |
|---|---|---|---|
| 客户 | 主档维护、身份核验/冲突/重复处理（治理拟新增） | 查正常客户、代客销售；不随意新建重复档案 | 手机号授权匹配、本人资料/服务/订单（拟建） |
| 商品/单位/价格/套餐 | 唯一维护入口，套餐独立定价及组成 | 读取/后端报价/销售；套餐已有ab3f8ea源码，待独立复审与联调 | 公开只读/单品交易分期，线上目前拒套餐 |
| 采购/库存 | 建采购、管理货位、调拨/盘点与审计 | 收实际到货、查货、核对原批次交货 | 只看允许公开的可售/履约，不看成本和货位 |
| 销售/资金/售后 | 完整POS及赊销/还款/退款授权与核账 | 个人账号现金销售，套餐已有源码待复审；原请求恢复 | 本人订单/真实支付与售后申请待完善 |
| 仓库作业/配送 | 查看原单剩余与任务、派单/改派、异常处理 | 整单多货准备/原请求交货、本人签收 | 看真实交付，不让客户操作员工确认指纹 |
| 权限 | 员工/角色/菜单独立授权 | 个人账号与真实岗位权限，常用仅布局 | 客户本人资源，不切换员工权限 |
| 农技 | 知识审核发布、复杂个案审核、分配/回访（拟新增） | 资料采集/标准答复/学习（拟新增） | 提问/回复/回访及受限AI（拟新增） |

一店一台电脑主要服务管理与复杂核账；员工不共用老板账号，也不为每人配电脑。后台不能成为手机每次正常销售或交货必经的人工审批瓶颈。

## 4. 数据与接口不可改变的边界

- 同一客户主档、商品/单位、订单、原配送和批次账，不为手机新建镜像业务系统。
- 库存读取需区分inventory投影与实际可出库批次；已知有效期参与FEFO，未知不造日期。库存移动保留原单位与来源，提货确认不再次SALE。
- 商品与套餐均后端报价；套餐按整数分分配到真实物料，原组/套数快照和0元物料保留。手机选套餐不自行展开或猜价格。
- payAmount表示含赊销净应结算；退款、实还、冲欠和现金实收分开。客户合并不把原支付类型4与还款类型4混同。
- POS UUID请求协调器、收货原请求和提货/配送指纹沿既有服务；未知冻结不换号。客户端创建防重与平台支付仍独立待实施，不能冒用员工staffId。
- 客户身份治理的任何新接口均属拟新增；手机号授权先服务端核验，同号不直接开放历史资金；空壳合并与双方有业务核账分级。
- 当前客户详情等宽DTO、旧qrBind、安全认领、AppID范围均须按客户端手册逐项改造，不能仅在后台新增按钮。
- 新表/字段先说明现结构不足、最简单方案、迁移/兼容/回退；保持同Flex事务连接，勿改旧V140迁移校验和。

现接口权威入口为api-admin各Controller→应用服务→domain/基础仓储；两端手册已列移动相关精确路由。后台全接口清册后续按真实Controller导出和复核，不在本轮编造不存在的“合并API”。

## 5. 关键操作流程

### 客户治理

后台待关联/重复线索→两档案对比与核验→固定源/目标和影响预览→锁下重查资格→执行一次→查原结果/审计。仅同人且无历史业务空壳可首期合并；双方已有业务明确阻断转专项核账，不删除原档案或改旧单客户ID。解除/合并后使旧会话失效。

### 手机销售到库房

员工自己登录→单品/套餐后端报价→原POS开单→后台同单可查→按实际交付方式进入原任务/配送→手机看整单实际物料→准备勾选→最新余量与原指纹确认实际交货→后台核对剩余。

多人可同时看到任务不等于系统已实现认领；首期明确一人作业约定，持久认领/移交若需要须另设计。防重提交只能防重复写钱货，不能防两个员工实际搬同一批货。

### 农技服务（未来）

客户确认资料→同case分配给员工采集→标准知识可直接服务/复杂问题进老板审核→回复→真实回访→经同意脱敏形成知识草稿。知识发布和专业个案审核分别授权，不让模型或普通员工自称老板批准。

## 6. 实施顺序、依赖与验收

1. **先员工营业闭环**：整合版验收、手机套餐、整单多货核对。后台仅补确需的同单视图和异常可读性，不横向重构全部页面。
2. **客户身份地基**：手机号登录、后台身份处置、重复对比/空壳合并、防重与审计。涉及已有业务的合并作为单独专项，先有阻断和核账路径。
3. **服务与知识**：后台审核/发布/队列与两端同步实施，先人工与标准知识，再受限AI。
4. **客户交易**：公开目录/报价/创建防重、正式支付/补偿/对账与履约；条件不齐只发布服务范围，不开放假支付。

每阶段验收必须绑定前后端提交、迁移/环境、岗位与设备、原请求/单据、API和只读SQL。延续员工A01—A12/B01—B03与客户C01—C17，另补：

| 编号 | 联动核对 | 通过标准 |
|---|---|---|
| ADM01 | 手机单品/套餐/混单各1，后台打开同orderId | 原价/成交分/组套数/实际物料/支付和归属一致100%，无第二单、无重复钱货 |
| ADM02 | 一单20项以上多货、分次交付、退货插入 | 后台/手机同一剩余事实；未交漏项0；提货新增SALE0；旧指纹0放行 |
| ADM03 | 客户先线上/先线下、不同号同人、同号不同人、并发关联 | 错绑/旧账泄露0；同请求10次重放只1治理结果；有业务合并明确阻断 |
| ADM04 | 后台改角色/停用/改派，手机保留旧页面 | 下一次真实请求按最新权限/指派拒绝，旧会话/响应不覆盖新身份 |
| ADM05 | 手机分次收货、后台查询批次和库存 | 原数量单位/8位有效进价/日期与摘要一致；同请求只1收货；未知不伪造0 |
| ADM06 | 3个岗位各2轮无需共用账号操作 | 不占电脑即可完成已授权日常任务；后台可追溯实际操作人；无权限扩大 |

当前只完成文档更新，不把这些目标标成测试已过。现有测试数字只属于97040d6历史证据；发布前按新代码运行并记录。界面继续沿根DESIGN，客户与员工按移动规范，不为三端强行统一字号或把宽表格搬手机。
