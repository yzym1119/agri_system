# 库存展示、销售拦截与新增权限决策

日期2026-11-09；版本V1.0；核查代码c394a83（无运行环境验收）。用户明确：有效期资料仅供门店大致参考，不应按该字段硬拦普通销售。本文件是当前授权决策，取代此前设计中“过期日期自动排除销售”的要求；**本轮只落实核查及决策，产品代码尚未按新规则修改**。

## 一、核查与纠正

| 问题 | 实际源码结论 |
|---|---|
| 后台库存列表读inventory.quantity | 属实，InventoryRepositoryImpl.findPage；只看有库存也按该投影过滤。当前字段totalQuantity是主单位在手投影，不是批次可出库量 |
| 员工单品目录排除过期、扣预留、只启用货位 | 属实，InventoryBatchBalanceMapper.findSaleableStock；真实销售与调拨select(...true)亦排过期 |
| 后台POS完全没有零库存加购拦截 | 不准确。admin-web/src/views/pos/components/ModernGoodsPanel.vue的handleCardClick已按item.stock<=0拦截；扫码亦经该函数。问题是stock来自旧投影/旧套餐库存，非统一批次口径，且父购物车合并、改数量不能仅靠卡片守卫保证库存充足 |
| 员工套餐与单品可售条件一致 | 不属实。ProductPackageApplicationService.calculatePackageStocks用sumAvailableBaseQuantityGroupedByProduct，后者仅按店汇总余额减预留，无单品同等货位/原单位证据核对。即使取消日期限制，这个差异仍需修 |
| 新权限只写文档即可生效 | 不成立。sys_menu必须真实落权限项，角色关联必须真实授予；V72/V127有历史超管授权，V134则只增加本人配送权限项、不自动授任何角色，不能把某一种历史迁移当全局固定规则 |

## 二、统一库存规则（已决定）

1. 后台库存页保留“在手量”，新增并列“当前可售量”，不把原totalQuantity简单改名。原单位投影和基准单位必须明确换算再同屏比较，不拿100袋对60瓶。
2. 在手量解释为实际已入账的全部在库余额；可售量为当前店、启用货位、扣除预留的合法批次余额，原基准单位证据不一致返回待核对，不猜0或盲加。投影与实际账不一致须标待核账，不能为让两列一样改流水。
3. **有效期不再是普通销售/正常调拨的自动排除条件。** 保留日期、日期未知和参考日期已过提示；可继续按已知日期优先排序，但不因日期跨天改变数量资格。提示不得另设隐含审批/强制切模式才能卖。实物检查和实际停售决定不由粗略日期字段替代。
4. 预留仍扣除，避免同一货重复承诺；停用货位仍不参与正常销售，避免把已停用位置当可作业库存。货位仅表示停用操作范围，不等于“日期到了自动停用”。若全部货位启用、无预留且单位证据完整，在手量与可售量应相等。
5. 库存页筛选分别明确“只看有在手库存”“只看有可售库存”；不悄悄改变旧筛选含义。销售页主显示可售量，日期风险留详情和库存预警。
6. 日期提示是质量参考而非适销资质结论；本规则只定义本系统日期字段的技术用途，不自动推断每件实物适合销售。

## 三、零量与不足的交互（已决定）

- 两端已知可售0均不允许加入清单；未知量或单位证据异常明确待核对，不当作有货或0。
- 有货时允许正常选货；改数量/重复扫码合并时提前提示不足。不能只比较每行与库存：同商品跨单位/多个套餐及单品混单要按合计物料需求核对，复用后端单位和套餐物料事实，不在UI造第二份折算/拆分逻辑。
- 零量但有实物：引导原采购收货、调拨入账或有权限的库存核账，不提供“忽略库存强制收款”、负库存或虚构批次/成本。
- 选货展示是快照，不锁货；最终仍由原交易在锁下复核并原子提交钱货。报价/库存预检不等于已收款；未实际外部扣款而事务失败不得写成“已收后回滚”。
- 初始库存不足应在选货/核对时可见；并发售罄仍可能最终拒绝，需要明确提示并沿原请求恢复，不改UUID重收。

## 四、新权限落地（已决定）

“本人订单”业务编码拟采用order:own:query，实施前查现菜单是否已占用；权限不是仅文档字符串。

- 随本人订单功能提交新增Flyway迁移，幂等加入现sys_menu，编号取实施时最新可用值，不改V140等已执行文件。无需新权限表。
- 不写死role_id=4，不给所有员工自动授权。沿V134最小原则仅增加权限项；实际管理员保持现有真实管理员授权机制，验收确认管理员能管理该项，不能默认固定role_id=1必为真实超管。
- 由后台角色管理明确给销售岗位勾选，库管按需；不能为了手机查询授整店order:query。部署手册同时给出“迁移→管理员授权→员工刷新身份→验证”步骤。
- 权限校验之外，服务端固定实际staff_id和store_id过滤列表、详情逐次核归属；不接受客户端staffId作可信范围。缺历史员工证据不猜本人。
- 测试涵盖菜单存在/缺失、未授权403、明确授权可查、别员工/别店详情拒绝、撤权或停用后拒绝。不用仅在夹具插关联证明部署已可用。

## 五、实施范围与验收门槛

下一实现批次先按本文件：

1. 同时调整InventoryLedgerService销售/调拨筛选与单品目录查询，移除日期资格限制，保持锁/事务/库存唯一事实不变；更新原日期边界测试，不扩大预留或货位资格。
2. 将套餐目录可售套数与单品同源：按当页物料批量读相同合法余额，核原基准单位；合并套餐中重复物料需求后向下整除取小。异常配置返回未知/不可售原因，不把配置问题伪装成确定零。
3. 后台库存列表新增可售字段/单位/状态与明确筛选；后台POS改读同一可售源，移除旧投影兜底。员工相应修改“排除过期”的提示，两端保持一致。
4. 在单品/套餐混合数量核对处补真实后端合计物料预检或复用等价现服务；不要引入新库存模式或预留机制。最终锁下出库不可被预检替代。
5. 本人订单实施时单独落权限迁移/配置手册/实际岗位验收，本轮不提前建空权限入口。

至少验证：昨天/当天/未知日期均可计入并正常出库；预留/停用仍排除；不同店不混；原单位异常未知；零量两端拦截；多个套餐/单品共用物料合计不足；不同销售单位换算；日期变化不改变可售量；出库重复请求只1组钱货；既有退货沿原批次回库及提货/签收不再扣库。库存表在手/可售按同单位逐项核SQL，不能只对比恰好无预留的种子数据。

本文件未运行产品测试、未修改数据库或部署。历史报告的过期排除测试仍是当时有效证据，需标新决策已取代，不倒改历史成绩。
