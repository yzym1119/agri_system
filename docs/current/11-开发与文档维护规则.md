# 开发与文档维护规则

版本V1.0，2026-11-08。根[AGENTS.md](../../AGENTS.md)仍是执行约束权威入口，本文件整理维护方式，不替代或放松原契约。

## 业务修改

修改前说明入口、模块、数据与验证影响；新增功能说明为何需要、解决什么问题、是否有简单方案。不随意加表、不为假设需求加模式/第二套账。保持高内聚低耦合，Controller不承载业务规则。库存、价格、退款、请求恢复、权限/门店边界沿AGENTS与当前真实服务；不可用UI隐藏代替后台授权。

## 文档统一原则

1. 现行正文放docs/current，固定中文语义文件名；日期、版本、源码基线、文档状态写在正文。旧路径只跳转，禁止两份现行正文各自修改。
2. 当前状态放02，详细设计放03/06/07，规范放04/05，运行放10，待办放12；不要再把每轮工作摘要当新设计总纲。
3. 每次修改接口/字段/状态/权限/业务范围，同提交改对应端手册、三端协同和验收项。只改布局不重复描述数据库设计。
4. 记录“已存在（源码）”“待实施”“须改造”“自动测试/HTTP/工具/手机验证”“未验证/历史”。日期旧不等于无效，测试证据旧不等于失实。
5. 不覆盖历史审查结论；发现旧文档错误在顶部加纠正与替代入口，保留原证据范围。仅真正被替代的设计标历史，仍有效规则保留。
6. API计划必须写拟新增，不把路径清单当已实现；新字段/表说明必要性、现有结构不足、迁移与保留事实回退。数据库现结构以源码迁移和目标库历史为准。
7. 旧链接保留兼容跳转，代码字符串路径不用机械替换成文档路径。引用源码应说明仓库相对路径，迁移文档后重算Markdown相对链接。
8. 不在文档写密码、密钥、token、真实客户明细；Mirror只同步已授权本项目摘要，不能记录凭据。

## 审查与发布门禁

先按当前源码核事实，完整设计经独立可实施性审查；产品风险验证采用真正对应的数据与行为断言。文档修改不需要重复跑无关全产品测试，但应验本地链接、围栏、入口及分类清单；不能因此声称产品测试新通过。

功能完成须对应可复核提交/环境与测试；总体完成度不用页面数或未经定义的百分比替代。未验真机、未接平台支付、后台治理待实现等必须显式保留。
