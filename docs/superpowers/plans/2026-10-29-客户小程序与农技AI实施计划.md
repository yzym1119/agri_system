# 客户小程序与农技AI实施计划

> 历史设计/计划（2026-10-29快照），保留追溯。当前范围、实现状态、接口与实施验收请读[V2.0设计与实施手册](../specs/2026-11-08-客户端小程序详细设计与实施手册.md)；本文“未创建/拟新增/未开放”等描述不得直接当作当前事实。


> **供后续执行者：** 使用 superpowers:executing-plans逐项执行。本文是设计待评审后的实施合同，不是已实施结果；不得先建表/购买模型再声称完成设计。写失败用例→运行失败→最小实现→运行通过→中文本地提交。

**目标：** 建立大庆及适用东北客户的可信种植服务入口，通过可追溯农技知识、照片/语音采集、真实回访和后续交易形成持续服务。

**架构：** mini-customer独立Uni-app Vue3/TS微信构建，复用员工计划E0—E1的纯TS合同库；api-client服务本人业务，api-admin负责授权员工处理与知识发布。农技事实放同一MySQL的新领域结构，原钱货账不复制。

**技术：** Java17/现有Spring Boot及Flex、MySQL/Redis、对象存储、Vue3/TS、受限模型Gateway。模型、语音供应商和具体版本在授权后的技术验证选择；不预设已购买资源。

**设计依据：** [客户端设计](../specs/2026-10-29-客户端小程序设计与实现.md)、[共享数据及AI](../specs/2026-10-29-共享数据与AI助手实现.md)、[总体调研](../specs/2026-10-29-双端小程序-调研与总体决策.md)。

## 全局约束

- 正文18逻辑像素、触点至少48×48，语音同时有长按与点击入口；拒绝定位/相机/麦克风仍有替代路径。
- 客户身份取登录态；不能靠手机号文本、昵称、请求体ID认领历史资料。首期老档认领均需独立授权的门店历史归属核验。
- AI不确诊、不自主给出药剂/混配/剂量，不读其他顾客或内部知识；旧知识撤回后停止新引用。
- 普通已审核知识可自助使用，不把每个问题送给老板；预约首期是待确认意向，不是已锁名额。
- 原订单、库存、退款、信用、积分/提成共用现有事实链。微信真正到账、验证、退款和对账未完成前不开放假支付。
- 每次迁移先说明现有结构不足，使用当时最新版本，不预占Flyway编号；私有备份、随机新库验证、向后兼容、禁止删除钱货事实。

## 审查重点

1. 当前手机号持有人认领了前持有人的钱包或历史订单。
2. 模型把不适用地区/作物、未发布内部内容或别人照片当知识引用。
3. 老板队列被所有普通问题堵满，系统未真正减少重复劳动。
4. 交易、上传、AI调用超时后新请求重复计费/落单或泄露旧会话资料。
5. 农户大字/方言/拒绝权限时无法完成核心任务，或AI解释隐藏了关键条件。

## C0：公共入口、基础工程与登录认领

**文件：** 新增`mini-customer/src/{App.vue,main.ts,pages.json,manifest.json}`、`pages/{home,profile,login}/index.vue`、`services/auth.ts`；修改`AuthService.java`及`AuthClientController.java`；拟新增`CustomerIdentityClaimService.java`、客户认领HTTP/服务测试。

**接口：** `getCurrentCustomer()`只返回当前有权资料；`createClaimTicket(customerActor): ClaimTicketVO`；`bindVerifiedIdentity(ticket,targetCustomerId,requestKey,evidenceRef,reason,staffActor): ClaimResult`。首期是老板线下核验后执行的一次原子绑定，不建设多级审批系统。

**持久事实提案：** 新增`customer_identity_claim_log`，只保存`request_key/hash、identity_id、source_customer_id、target_customer_id、approved_by、verification_method、reason、evidence_ref、approved_at`及绑定结果；`uniq_identity_claim_request(request_key)`约束，原绑定与日志同Flex事务提交。理由：现有customer_identity只保存当前关联，客户备注无法证明谁凭什么把历史钱包归属改变；普通异步操作日志不能保证与绑定原子。表为正式实施时待审迁移，本轮不创建。无变更正文的证据文件由受控存储保管，日志不存身份证照片、验证码或OpenID明文。

票据用安全随机值，服务端绑定当前identity和临时客户，短期有效；QR仅含票据，不含原顾客电话/余额。票据只定位，不替代门店历史归属核验。单次绑定取得身份及客户锁后重核全部条件；同requestKey重放返回原结果，改目标/原因/证据拒绝。批准后使原临时客户会话失效，再以微信登录取得原客户身份；失效操作失败可重试，不能回滚或重做已提交绑定。

- [ ] 先写客户token/员工token互斥、停用/不存在、当前手机号相同但历史客户不同、旧档重复电话、绑定冲突、临时档已有任意私有事实的失败用例。
- [ ] 读取当前AuthService新OpenID自动新建客户行为，保留稳定客户ID；新增认领时锁身份及稳定顺序客户，核验门店人工批准和历史归属证据。只重绑明确身份、不搬钱包余额或订单。
- [ ] 暂无可靠手机号能力时仅人工核验，不用开发登录替代。切换身份使旧会话失效，重新签发并隔离缓存；未认领只能看当前身份本人资料。
- [ ] 公开首页、门店和知识入口无须先注册/授权定位；跑HTTP与真实数据库认领并发、会话隔离测试，再做真机首次使用；中文提交。

**重要边界：** 上述绑定日志与票据尚不是现有能力；若暂不实施，保持不认领并由门店另行处理，不提供“先绑后补审计”的简化入口。不能把这个任务标为“只改一条customer_id”。

## C3：照片、语音与受限AI请求

**文件：** `application/agronomy/assistant/{AgronomyAssistantService,ModelGateway,KnowledgeRetriever,AnswerValidator}.java`、infrastructure供应商adapter；两端`services/assistant.ts`与`pages/ask/index.vue`；测试集`core-application/src/test/resources/agronomy/assistant-cases.json`。

**接口：** `requestAnswer(caseId,requestKey,factsVersion,actor): AssistantRequestVO`；`getAnswer(caseId,requestKey,actor)`；`ModelGateway.generate(AllowedContext): CandidateAnswer`。AllowedContext只能包含已核验事实及可见知识片段，不能传原token/任意SQL/其他客户资料。

- [ ] 先写50个由老板审核标准答案的版本化评测：缺事实、普通知识、用药/混配/数字、知识冲突、过期、提示注入、私有身份、模型超时和重复请求等。
- [ ] 上传先检文件归属、大小、类型和真实媒体内容，图片移除非必要EXIF；获取短期受限URL，不允许用户输入任意远程URL给服务端/模型访问。
- [ ] 接入前取得模型供应商与数据处理授权，确认适用备案/登记和标识；先用虚构样例，真实顾客资料不能随工程测试上传。
- [ ] 资料转写后用户确认；后端先按发布策略判定是否可用标准知识，再允许生成解释。客户自动回答优先显示已审核标准卡片；AI不得额外合成药剂、混配、剂量或诊断结论。
- [ ] 保存AI原requestKey与处理状态，生成不持长数据库锁。模型超时/结果未知不自动重新发起另一次付费调用；先查原结果，显示知识/人工替代。若供应商无查询/幂等能力，明确这次结果未知，不承诺“绝不重复计费”。
- [ ] AI请求处理元数据与不可覆盖的用户/回答正文分开：请求entry的处理状态可受控更新，输入正文不改；输出追加独立关联entry。唯一请求身份与结果关联在真实MySQL验证，不能因“entry追加”而重复生成。
- [ ] 所有引用经服务端验证后才显示最终建议，人工未审核不得标人工结论；无依据转补资料/人工，模型置信分数不作病害准确率。
- [ ] 测越权/危险自动处方0例放行、引用真实可见100%、失败降级及预算保护；逐例老板确认实用性；中文提交。
