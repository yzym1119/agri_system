# POS异常恢复实施计划

目标：已批准的异常收银恢复闭环。保持现有开单、资金及原批次库存事务；不增加支付渠道或订单模式。采用现有分支和工作区，保留原预览库与API，测试使用隔离环境。

设计：客户端在发送前保存UUID请求号和原核对摘要。新增pos_sale_submission表，唯一请求号绑定真实门店/员工；记录请求内容SHA256、成交订单ID及COMPLETED/CANCELLED状态。提交先插入并锁请求记录，再调用原createPOSOrder，在同一Flex事务保存成功结果。失败全回滚。核对查不到仅表示尚无已提交结果；结束未成交请求须插入/锁同请求号并保存CANCELLED屏障，迟到请求会被拒绝；并发成功则返回原成交结果。成功重放只返回原订单，相同请求号改内容拒绝，跨员工/店拒绝。不以Redis或sessionStorage作为成交权威。旧无请求号记录不允许自动解冻。

1. 新增测试：请求成功重放只写一单、内容冲突、取消与迟到提交、跨身份、失败回滚。先运行失败，最小实现请求仓储、应用协调服务及V133迁移；服务职责在应用层，Controller仅鉴权与转发。
2. 前端测试：先持久化请求号再发送，结果未知只读核对，取消必须后台屏障确认；成功恢复不重复收款；登录/切店旧响应不污染新对象；旧无身份记录保持人工核对。先红后绿，实现API与原POS页恢复区，沿用公共样式。
3. 自动验证：后端全verify、真实MySQL新迁移及并发取消/成交/回滚、前端全测试和构建；补HTTP权限入口契约。
4. 实际浏览器验收：隔离环境单据；查看请求核对及安全恢复，核对原订单、收款、库存数量不重复。保存截图、只读SQL与报告。独立审查后保存本地提交及Mirror项目记录。

重点：GET读到不存在不是未成交证明；取消与提交必须同一行锁且同Flex事务；结果未知不能自动取新请求号再提交；请求记录无验证码明文；历史记录不造身份。迁移新增表因为失败请求在订单表没有载体，不能把取消屏障塞进备注或伪造零元订单。无需修改历史业务数据。
