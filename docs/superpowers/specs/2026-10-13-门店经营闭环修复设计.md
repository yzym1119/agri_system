# 门店经营闭环修复设计

日期：2026-10-13。用户已要求按顺序执行：固化已验收成果、赊销退货与还款、门店人工配送、权限及真实页面验收。

## 目标与边界

完成小门店的一张销售单从收款或赊销，到实物交付、还款、退货和日终核对的闭环。使用现有库存账、订单、应收、还款、售后和配送表，不建立新价格来源、库存模式或新的账款调整表。用户可观察的结果是钱、货、欠款均能追溯到原销售单，重复请求和并发操作不会重复记账。

真实微信/支付宝网关与商户配置、跨店调拨审批、更多促销策略仍不属于本轮门店闭环。

## 顺序与基线

固化前先修已复现的POS支付缺陷：优惠券不能触发完整支付后又扣钱包；现金及混合支付可正常使用优惠券；支付明细必须逐笔为有效类型、正金额、精确到分。单一/混合钱包使用同一真实金额拆分，并消费对应本金验证码；流水不能与实际扣减不同。优惠券取得锁后核销一次。

完成验证后，在本地 `codex/` 分支形成可回退的基线提交，再开始账款和履约修改。只提交本项目可审查文件，开发库备份及构建产物保持忽略；不推送、不部署。

## 赊销和退款资金契约

订单 `payAmount` 统一表示优惠后的净应结算额，包含赊销部分；实际已收款与未还欠款根据支付和应收事实展示。纯赊销不能再把净金额清零。退款上限与套餐净金额分摊都使用原净应结算额。

设原净成交额为N、原非赊销收款为C、原赊销为B、原单累计实际还款为P、已完成退货冲欠款为W、已退收款为F、累计成交冲销为R。必须满足：

```
N = C + B
原单剩余欠款 D = B - P - W
R = W + F
N - R = (C + P - F) + D
```

本次成交冲销额r先冲原单未还欠款：`w=min(r,D)`；退已收款为`f=r-w`。只处理原单，不能核销或退回别的销售单的资金。例：纯赊100、未还、退30，欠款70、退款0；已还40、退80，冲欠60、退原还款20。

`credit_amount` 保留原赊销事实，`paid_amount` 保留累计实际还款，退回还款不减少该历史累计字段。退货冲欠款保存到已有售后记录，资金来源实际已退保存到原收款记录。每次检查原单及来源累计金额守恒。

`after_sales.refund_amount` 表示成交冲销额。新增两项实际处理结果：冲欠款金额、退已收款金额，相加必须等于成交冲销额。`cashRefundAmount` 在用户页面显示为“退已收款”，包括本金钱包和专用金，不仅指纸币现金。

原支付与明确分配到本单的还款按时间、来源类型和ID稳定倒序退款。原支付类型4表示本金钱包，还款类型4表示银行转账，不能混用编码。优惠券、赊销或未知类型不作为可退资金。未知类型和来源不足均在写入前拒绝，不能假扣待退款余额。全退恢复优惠券按累计成交冲销达到N判断。

## 还款事实、归属和并发

保留FIFO还款，但一次收款按实际核销的欠款单保存多条既有还款流水，共享同一还款流水号与请求标识；各条金额之和等于实际收到金额。列表按批次汇总，并提供原单分配明细。逾期但有余额的欠款也可还款。

请求标识必填。相同请求重试先返回原批次；金额、收款方式、外部流水或客户变化必须拒绝复用。员工身份与收款门店由当前登录员工派生，不能信任请求中的操作人。普通员工只处理本店欠款；客户全局额度的内部核对不能使用被门店过滤后的展示总额。

还款先锁客户，再锁本店欠款账户，按创建时间与ID核销；还款不再锁订单。退货先锁订单，再锁客户和原单账户及资金来源。使用READ_COMMITTED和当前读；所有冲欠款、退款计数、钱包变更、回库及售后完成共用一个事务。

## 最低结构修改

不新增表。V132在现有表增加7字段：

| 表 | 字段 | 作用 |
| --- | --- | --- |
| credit_account | store_id | 从原订单确定门店，使用现有租户隔离 |
| credit_repayment_log | credit_account_id | 记录实际核销的原欠款单 |
| credit_repayment_log | request_key | 还款请求防重及批次分配关联 |
| credit_repayment_log | refunded_amount | 原单还款来源累计已退 |
| order_payment | refunded_amount | 原支付来源累计已退 |
| after_sales | credit_reduction_amount | 成交冲销中的冲欠款部分 |
| after_sales | cash_refund_amount | 成交冲销中的退已收款部分 |

原订单应收账户增加唯一约束；还款分配按门店、请求、欠款账户建立唯一约束。新增金额精确到分，累计不超来源原金额。

历史账户门店仅由原订单回填，重复账户、缺原单和不守恒数据停止迁移。纯赊销旧净金额0，仅在净成交、原账户及赊销支付事实一致时回填，不重放完成事件、积分或客户统计。旧还款缺少分配时留空，不按当前FIFO猜测回填。历史已退款来源无法确定时保留未知标记并拒绝继续自动退款/收还款，提示核对；不能把未知金额当作0重新开放可退资金。本机开发库空业务数据可直接升级，不再次清库。

## 门店人工配送

POS默认当场交货。选择门店配送时来源仍为POS，使用既有收货人、电话、地址和配送单字段；无收货信息在收款及出库前拒绝。创建待配送记录后按原销售流程立即出库并记成交、收款/赊销及绩效。

配送履约独立读取既有 `delivery_status`。派单与签收不再次出库或收款。POS成交时已经结算，签收不重复首次结算；线上订单仍按其现有签收结算口径处理。

派单、签收、退款共用原订单锁。处理中售后暂缓交付；已完成部分退货后可交付剩余实出库物料，保留订单退款状态，不能用状态6覆盖状态9。全额退单停止配送，未退0元物料继续走回库；无剩余物料不能派单。

同城配送必须人工签收。快递自动收货若保留，按实际发货时间进入统一锁单确认入口，同步配送签收时间和完成事件，不直接改订单状态。

## 权限与页面

角色POST只创建，拒绝传入既有ID；服务端生成角色编码，不能借请求创建ADMIN/SUPER_ADMIN身份。创建或编辑不写菜单权限，非空菜单授权请求明确拒绝；授权只走现有独立授权接口。真实权限测试应加载SaToken拦截器。

页面显示成交冲销、冲欠款、退已收款及还款原单分配。配送操作依真实配送状态显示，部分退货后仍可处理剩余配送。还款请求标识在打开一次收款操作时生成，失败重试保留，同一新收款才更新。

## 验收结果

1. 优惠券与现金、单一余额、混合支付可成交，资金只扣一次；无效支付金额/类型不落事实。
2. 纯赊销、混合支付、未还、部分还款、已还清及分次退货满足上述资金恒等式，原库存批次回库、提成回冲不超额。
3. 相同还款请求重试、双还款及还款与退货并发只产生正确的一组事实；普通员工不能处理其它门店账款。
4. 同城POS开单、派单、部分退货、签收及重复/并发操作不重复扣库或结算；同城不自动签收。
5. 真实浏览器以老板、收银、库管身份完成采购、分次收货、单品套餐混卖、收款/赊销、还款、配送、退货；日终钱、货、欠款可核对。
