# Working State

最后更新：2026-09-28

## 用途

这份文档只记录当前仍然有效的开发事实，供后续每次继续开发时快速对齐。
不要把历史交付文档当成当前状态，历史资料仅用于追溯背景。

## 当前判断

- 项目已不是早期骨架，后端主业务模块、管理端页面、数据库迁移都已落下较多内容。
- 业务覆盖范围已经超出“农资进销存”，实际是“交易 + 会员 + 营销 + 售后 + 赊销 + 绩效”的门店经营系统。
- 当前更像“主体功能已铺开，但关键闭环和安全性还未收口”，不适合继续无节制加模块。

## 零售事实链改造（已交付，休眠待激活）

- 目标：把「商品多单位 → 实际收货批次 → 批次货位余额 → 销售行批次归属」做成单向事实链，收银员只扫商品码/批次码、不选批次，批次证据分级（`SCANNED`/`FULFILLMENT_CONFIRMED`/`RULE_ALLOCATED`/`UNKNOWN`）。
- 设计权威：`docs/superpowers/specs/2026-09-06-retail-unit-batch-cost-price-design.md`；执行计划：`docs/superpowers/plans/2026-09-06-retail-unit-batch-cost-price-plan.md`（Task1–10）。
- Task1–10 已全部交付并合并 master（`ed90bdb`）：迁移护栏、SKU 多单位、收货事实、批次货位余额、库房取货与销售批次证据、批次成本毛利、价格引擎与改价留痕、风险建议与人工决定、管理端作业界面、历史确认 + 灰度切换 + 三层对账 + E2E。
- **当前仍为休眠态**：未对任何 SKU 执行 enable，legacy `inventory`/`inventory_batch` 行为不变。激活必须按 `docs/runbooks/retail-fact-chain-rollout.md` 执行，逐 SKU 人工确认、可回滚；**未按 runbook 完成历史库存确认与对账前，禁止 enable 任何 SKU**。
- 迁移号约定：当前已到 V128，新迁移从 **V129** 起。

## 提成冻结生命周期

- V118/V122 已落地提成冻结与解冻（`CommissionUnfreezeJob`），开关 `performance.freeze-enabled` 在 dev/test/prod 均默认 `false`，即当前提成不冻结、直接入账；开启后按退货窗口冻结再解冻。

## 本轮已完成修复

- 客户端订单、售后、积分商城接口不再信任 `X-Customer-Id`，改为统一从 Sa-Token 登录态解析客户身份。
- 客户端订单详情新增客户归属校验，客户端确认收货接口已接通。
- 钱包验证码发送接口已从公开接口改为登录接口，并绑定本次计划支付金额。
- 钱包验证码新增有效性校验接口。
- POS 余额支付消费验证码时，已增加客户、金额、状态、过期时间校验。
- 订单支付中的优惠券已增加客户归属校验，并补上商品分类限制所需的分类解析。
- 小程序支付已调整为两段式：首次调用只返回预览，外部支付确认后才真正落支付、改订单状态并扣库存。
- 小程序支付接口已进一步拆分为 `payment-preview`、`payment-intent`、`payment-confirmation`，不再依赖在 `/pay` 里塞确认标记。
- 已新增 `order_payment_intent`，支付发起参数会先落库；客户端确认和公开回调都基于 `intentNo` 做幂等确认。
- 订单主支付方式与支付流水类型已彻底拆开：`order.payment_method` 与 `order_payment.payment_type` 现在使用两套明确编码，不再保留 `payment_type=3` 同时代表“余额/支付宝”的兼容判断。
- 订单详情 / 列表 / 小票所需的支付展示名已改为后端直接计算并返回，避免前端继续各自猜测 `payment_type` 的历史歧义。
- 管理端订单直接退款已补上整单退款回库；售后退货已支持商品维度回库，但订单模块自己的直接部分退款接口仍主要是总金额口径。
- 已新增 `V101__unify_payment_codes.sql`，用于把旧测试数据中的 `payment_type=4` 迁到专用金 `8`，并把无外部流水号的旧 `payment_type=3` 迁为本金余额 `4`。
- 管理端 POS 下单的验证码分布式锁已改成按新支付编码判断，不会再把支付宝条目误识别成钱包支付。
- 套餐管理接口已补齐 `package:query/create/update/delete` 权限校验，并新增初始化权限迁移。
- 管理端 POS 的价格规则匹配与主辅单位换算已抽成统一前端工具，不再在 `pos/index` 和旧 `CashierPanel` 中各自维护一套不同口径。
- 后端已新增统一商品定价服务，小程序下单与 POS 下单在未显式传单价时，都会按“策略价 -> VIP/普通降级 -> 商品基础价 -> 主辅单位换算”自动解析单价，不再直接退回商品零售价。
- VIP 价格解析已在后端补上过期降级策略，过期 VIP 会按普通客户口径匹配价格规则，不再继续命中 VIP 价。
- 售后退货回库已补上按原订单行单位做主辅单位换算，避免辅单位销售/退货时库存回库数量失真。
- 客户端下单已不再信任前端上传的 `unitPrice`，订单行价格统一由后端重新计算，避免客户端篡改单价。
- 管理端退货售后已补上历史累计校验，同一订单行不会再出现超量退货、超额退款；`9-部分退款` 订单也允许继续发起后续部分退货。
- 售后退款现在会同步发布订单退款事件，绩效扣减不再漏掉售后场景；退款事件也支持按订单行明细精确扣减，而不是只能按整单比例摊销。
- 订单模块自己的直接退款接口已补成“整单全退或带商品明细的部分退款”两种模式，部分直退会按订单行回库并附带明细退款事件。
- 管理端退款弹窗已开始按订单状态分流：`2/3/4` 走订单直退，`5/6/9` 走售后退货，前后端不再各自走不同口径。
- 订单列表、订单详情、小票的支付展示已统一改成“后端返回 `receivedAmount/creditAmount` + 前端共享 helper”口径，`payAmount` 不再直接被当成“实收现金”展示，混合支付带赊销时会拆开显示“已收/赊销”。
- POS 收银弹窗已补上钱包支付预估，会在提交前展示“专用金/本金余额”预计拆分，并限制混合支付中的余额金额不超过“本金余额 + 当前订单可用专用金”。
- POS 创建订单后端已增加钱包可支付上限校验，余额不足时会直接返回明确业务错误，不再等钱包扣减时才以底层异常失败。
- 客户详情里的“赊销/还款”页签已补成闭环视图：可筛选欠款单据、查看还款记录，并可直接生成赊销对账单；切换到其他客户时也会按当前页签刷新，不再残留上一位客户的数据。
- 库存调拨页面已接入管理端路由；此前数据库缺少对应菜单行导致侧边栏不可达，已由 `V128__restore_missing_page_menus.sql` 补齐（同时补齐库存日志、客户跟进页面菜单与工作台授权）。
- 角色管理已补上编辑接口 `PUT /api/admin/roles/{id}`：只改名称/状态并保留原角色编码，不改动菜单授权（菜单授权只经 `role:assign` 维护）。
- 月度绩效结算已跳过已确认工资单，重跑结算不会再覆盖已确认工资单导致二次实发。
- 小程序「客户端自行确认外部支付」已加配置闸门 `payment.client-confirm.enabled`（默认关闭，仅 api-client dev 环境开启用于联调），关闭时不会读取支付意图也不会落支付/扣库存。
- 工作台已不再是纯占位页，现已接通今日经营驾驶舱、赊销风控、库存资金占用、近 7 天销售趋势和滞销商品列表，管理端已有统一经营总览入口。
- 绩效管理已补成正式管理端页面并接入菜单，现可统一维护提成规则、员工月目标、工资单确认和员工绩效流水，不再只有后端接口可用。
- 系统设置下已补出“操作日志”页面，后端现有日志分页接口已有前端查询入口，可按员工和模块排查后台操作痕迹。
- 报表中心已补成正式页面并接入菜单，客户分析、销售趋势、滞销库存和导出接口不再散落在单独控制器或工作台摘要里。
- 管理端登录态现已回传员工权限集，`v-permission` 指令和侧边菜单开始真正按权限裁剪，不再是“代码里写了权限、前端实际不执行”的状态。
- 库存调拨页已补成“提交 + 最近结果回显 + 聚合历史记录”闭环，调拨记录不再只能从库存流水里人工拼接查看。
- 库存调拨已接入正式调拨主单 `inventory_transfer` 和批次明细 `inventory_transfer_detail`，调拨号不再使用临时时间戳，历史查询也不再依赖库存流水反聚合。
- 管理端已新增“当前员工菜单树”接口，侧边栏和默认落点开始优先使用后端菜单数据，而不再完全依赖前端手写菜单顺序。
- 管理端业务页现已改成登录后按权限动态注册到根布局，不再在初始化时全量挂载所有业务路由；登出时也会清理本轮已注册路由。
- 管理端业务路由已进一步抽成前端页面注册表，由注册表负责“菜单路径/权限 -> 页面组件”的映射，主路由文件不再继续堆积页面声明。
- 已新增 `V103__normalize_admin_menu_paths.sql`，开始把采购、库存、客户等历史菜单 path 统一到当前 Web 路由口径，减少前端 alias 和权限兜底匹配。
- 管理端高频业务页的动作按钮与页签入口已继续按后端权限点显隐收口，库存、采购、商品、客户、积分商城、员工、角色、营销、订单页开始避免“列表能进、按钮点下去才 403”或“单权限账号进页后半瘫”的半闭环体验。
- 商品列表里的“实时库存”列已接通库存接口聚合，不再是前端占位值；当前会按当前页商品汇总所有门店库存并异步回填显示。

- 赊销模块已补成独立管理页，数据库已有的 `/credit` 菜单终于接通到前端路由；现在可按客户查看欠款台账、还款记录、赊销额度与最近挂账时间，并直接执行还款、调额和生成对账单。
- 已新增 `V104__add_after_sales_permissions.sql`，补齐售后管理菜单和 `afterSales:query/audit/refund` 核心权限初始化。
- 供应商删除已补上采购单引用保护；已被历史采购单使用的供应商现在会被阻止删除，避免采购记录详情和列表丢失供应商名称。
- 优惠券模板删除已补上发放记录保护；已被发券的模板现在会被阻止删除，避免客户已领取优惠券失去模板归属。
- 积分商品删除已补上兑换记录保护；已有兑换单引用的积分商品现在会被阻止删除，避免历史兑换记录丢失商品名称。
- 门店逻辑删除口径已开始收口：活动门店查询会明确排除已删门店，历史订单/采购/售后/库存流水回显则允许读取已删门店名称，避免“删除后仍可被业务继续使用”或“历史页面门店名消失”两种问题并存。
- 门店删除已补上活动占用保护：仍有员工归属或库存余额的门店现在会被阻止删除，避免删除后留下“员工挂空门店”或“库存仍在已删门店”这类半残数据。
- 客户逻辑删除口径也已开始收口：活动流程继续只认未删除客户，但历史订单、售后、赊销台账回显已允许读取已删客户，避免客户删除后历史主页面丢失姓名和手机号。
- 员工“禁用/离职”状态口径已修正为 `2=离职`，不再把离职写成 `0` 导致管理端筛选、展示与后端状态含义不一致。
- 门店状态口径也已统一为 `1=正常，2=停用`，不再出现前端按 `2` 提交/筛选、后端文档和模型却按 `0` 理解的错位。
- 客户删除已继续补上进行中业务保护：若客户仍存在未完成订单、处理中售后或未完成积分兑换，将直接禁止删除，避免删除后把运行中的交易链路切断。
- 营销规则删除已开始收紧为“停用优先”：启用中的充值规则和 VIP 权益不再允许直接删除，需先停用后再删，避免把仍在生效的营销配置直接物理删除。
- 商品价格策略删除也已收紧为“停用优先”：启用中的价格规则不能直接删除，管理端现已补出启用/停用操作，避免仍在生效的定价策略被直接物理删除。
- 系统字典项删除已改为保守约束：启用项和默认项不能直接删除，且同一字典类型只会保留一个默认项，避免配置页维护把运行中的选项直接删穿。
- 套餐删除已进一步收紧：上架中的套餐不能直接删除，且被历史订单或启用中套餐提成规则引用的套餐也会被拦截，避免经营分析和绩效配置出现悬空对象。
- POS 商品面板的取数口径已收口为“正常商品 + 已上架套餐”，不再把停用商品或下架套餐继续暴露给收银台。
- POS 套餐炸开下单时已重新保留 `order_item.package_id` 来源标记，套餐来源商品行现在可以继续参与套餐提成匹配，不再因为“统一按商品下单”把套餐经营语义彻底丢掉。
- 绩效规则页已从“手填 targetId”改成按真实商品/套餐选择，规则列表也开始回显目标名称；后端保存时会校验商品、套餐、员工是否仍为有效对象，减少悬空提成规则。
- 绩效规则语义已进一步收口：充值提成、拉新提成当前按“全局规则 / 指定员工规则”生效，不支持配置目标对象；品牌推广仍是预留类别，结算链路尚未接通，管理端不再允许继续配置成可用规则。
- 库存列表里的“仅显示有库存”已改为服务端查询条件，不再由前端在分页结果上二次过滤；库存页分页总数和翻页结果已与筛选条件保持一致。
- 角色管理页已补齐角色状态维护，新增/编辑角色时不再只能改名称、列表却只能被动展示启停状态，角色基础配置闭环更完整。
- POS 开单已进一步收紧员工身份口径：后端现在只信任当前登录员工决定操作员和所属门店，不再允许通过请求体篡改 `staffId` 串改门店归属或冒用其他员工开单。
- 订单列表里的“订单来源”筛选已改成与后端真实枚举一致：`1=POS`、`2=小程序自提`、`3=小程序配送`，不再把“小程序”错误压成单值 `2` 导致配送单被漏筛。
- 订单配送链路已补齐一层真实落库：管理端同城“派单”时选择的配送员现在会写入 `order_delivery.delivery_staff_id`，订单详情也能回显配送员姓名，不再是前端选了人但后端完全忽略的假操作。
- 订单列表里的配送动作已按当前真实能力收口：筛选先统一到“自提 / 配送订单”，而对配送订单的“快递发货 / 同城派单”选择放到待发货动作里决定，避免继续把尚未稳定建模的配送细分假装成下单时已固化字段。
- 订单列表里的配送标签已开始按配送单真实数据推导：有配送员的配送单会回显为“同城”，其余配送单保持“配送”口径，不再把所有配送单都一概展示成同一种类型。
- 配送方式现在已正式落到 `order_delivery.delivery_type`：新增 `V105__add_order_delivery_type.sql`，老配送数据会按“有配送员=同城，否则=快递”回填，新小程序配送订单会在创建时直接生成配送单并固化配送方式，不再只在订单列表运行时猜。
- 管理端订单列表的配送筛选已恢复为真实语义：`1=自提`、`2=同城配送`、`3=快递配送`，待发货动作会按已固化的配送方式只展示对应操作；兼容旧测试单时，未固化的历史配送单仍允许继续处理。
- 订单确认收货现在会同步回写配送单状态和签收时间，避免订单已完成但 `order_delivery.delivery_status` 长期停留在“配送中”的状态漂移。
- 小程序下单现在会校验门店可用性：门店必须存在且处于启用状态，自提单还会校验门店是否支持自提，避免继续向停用门店或不支持自提的门店下单。

## 已确认问题

### P0

- 外部支付仍未真正接入微信/支付宝网关。
  现状：`payment-intent`、`payment-confirmation`、公开回调入口和幂等落库已经有了，但还没有真正生成平台支付参数，也没有完成回调验签。客户端自行确认入口已由 `payment.client-confirm.enabled` 默认关闭，只在 dev 联调开启。
  风险：当前链路只适合联调和本地开发，不能当成正式收款方案上线；公开回调入口在验签落地前同样不可对外暴露。

- 外部支付失败补偿和对账闭环还没完成。
  现状：支付成功路径已拆开，但支付超时、重复通知、补单、对账差异等异常场景还没有系统化处理。
  风险：后续一旦接真实支付，会出现“用户已付款但订单未完成”或“重复确认”的运维成本。

### P1

- 支付编码说明仍未在所有文档和初始化脚本中同步。
  现状：核心 Java/前端代码已统一，但旧迁移、旧 README、部分历史注释还保留旧口径。

- 管理端接口权限基本补齐。
  现状：套餐、角色编辑等已补齐；遗留一处待收口：新增角色接口 `POST /api/admin/roles` 携带 `id + menuIds` 时可绕过 `role:assign` 修改授权（既有行为，计划阶段 4 处理）。

- Web 端仍有少量业务页面残留“可打开但细节未完全收口”的问题。
 现状：高频页面的权限与主流程已基本收口，但仍需继续排查库存、POS、订单、客户等页面里的占位交互、快捷操作和边缘态表现。

- 绩效规则类别的业务语义不是完全对称。
  现状：销售提成按商品、套餐提成按套餐；充值提成和拉新提成目前没有目标对象维度；品牌推广只有类别定义，没有实际结算事件链路。
  风险：如果后续继续按“所有类别都能绑定 targetId”去扩展页面或接口，会再次做出看起来能配、实际不生效的伪闭环。

### P2

- 前端现在已按权限动态注册业务路由，菜单展示和默认落点也会读取后端当前员工菜单树；但数据库菜单路径仍有部分历史数据尚待迁移生效，当前仍保留少量兼容 alias。
- 调拨现在已有正式主单与批次审计明细，但仍是“一次提交即完成”的直达模型，还没有审批、在途、签收等更细状态流转。

## 架构判断

- 分层方向是合理的：`core-domain`、`core-application`、`core-infrastructure`、`api-admin`、`api-client`、`admin-web`。
- 当前实现还不是严格分层。
  现状：`core-application` 直接依赖 `core-infrastructure`，并直接使用基础设施实现类、Mapper、`JdbcTemplate`。
- 结论：短期可以继续开发，但中期需要做边界收敛，否则维护成本会越来越高。

## 接下来的开发顺序

### 依据：系统收尾计划

当前开发顺序以 `docs/superpowers/plans/2026-09-28-system-closure-plan.md` 为准：阶段 1（P0-A 小而硬的修复）已完成；阶段 2 真实支付闭环受商户号/支付资质阻塞；阶段 3 小程序端接口补齐、阶段 4 P1 功能缺口、阶段 5 P2 与文档，各自开工前单独写细化计划。下列分阶段条目作为背景保留。

### 第一阶段：继续收口 Web 端业务闭环

1. 继续排查管理端高频页面里的占位交互、假数据、边缘态和快捷操作，优先修 POS、库存、订单、客户、商品这些直接影响日常使用的页面。
2. 保持“页面入口控制 + 关键写操作控制”的权限粒度，不再继续做过细的按钮级打磨。
3. 继续把后端已有接口能力接到前端真实页面上，减少“接口有了但页面仍靠前端兜底/占位”的情况。

### 第二阶段：支付网关条件具备后，再接真实外部支付

1. 把 `payment-intent` 真正接入微信/支付宝下单参数生成，而不是只保存意图并等待外部系统确认。
2. 补外部支付回调验签、幂等冲突处理和失败补偿，而不只是开放一个确认入口。
3. 在具备商户主体、小程序支付申请和回调环境后，再做联调和对账闭环。

### 第三阶段：做结构整理和文档同步

1. 清理 `core-application` 对基础设施实现类的直接依赖。
2. 把报表类读查询与核心业务流程进一步拆开。
3. 统一更新 README、DDL 说明、模块状态文档，去掉过期口径。
