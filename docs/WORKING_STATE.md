## 当前库存结构（已统一）

- 收货批次、批次货位余额与移动流水组成唯一库存账；采购、销售、退货、盘点、调拨全部接入。
- 没有按 SKU 激活或选择 LEGACY/BATCH_LOCATION 的运行分支；旧表仅保留历史。
- 库存快照统一显示商品主单位，账本使用持久基准单位。新建商品同时建立单位，新建门店同时建立默认后仓。
- POS 和线上支付实际扣减库存并记录订单行批次成本；提货只核对出库证据，不重复扣减，多批次可逐项确认。

- MyBatis 与 JDBC 共用 Flex 数据源及事务连接，不能直接把 Boot 原始 Hikari 数据源接到写库存的 JDBC 服务。

## 当前价格结构（已收口）

- 档案价格均明确为元/持久化基准单位；零售价必备，会员价与最低价可选，0代表未启用。所有销售单位按持久化系数换算，不区分门店、渠道、会员等级或日期策略。
- VIP 有效性由 customerId 对应的客户档案决定；过期会员按零售价，会员价不能低于最低价。
- 商品多维策略只读，单独线上价不再维护。最低价只用于提醒/议价授权，不参与售价兜底。
- 单价议价与整单手工优惠共用 `order:price:override`，默认只授予超管。其他角色可通过现有角色管理明确授予；正常收银无需此权限。
- 议价记录保存标准价、成交价、原因及员工。整单优惠金额与原因保存到订单；历史成交价不会随商品调价改变。
- 收银展示报价与结算报价不一致时要求重新报价；报价失败整体拒单。前端异步报价不能恢复已删除商品，恢复挂单在标准价未变化时保留已谈成交价。
- V130 精确转换旧价格的计价单位，不改采购成本或历史订单；不能精确换算或价格冲突时迁移停止，不能猜价。
- 用户已明确把套餐独立定价纳入本轮。门店 POS 按套餐元/套价格收款，前端保留一行套餐，物料由后端展开；物料正常零售价只用作分摊权重，不覆盖独立套餐价。
- 套餐组、名称、套数、每套成交价随实际物料订单行保存；total_price 为按分分摊后的权威金额，unit_price 可保留12位参考精度。历史套餐行不猜测回填。
- 含套餐订单退货按原实付分配净金额，分次退货使用累计数量并结清尾分；0元物料仍回库并保留事实。直接退款与售后共用现有售后事实，重复/超退受订单锁约束。
- 套餐固定提成按实际套数计算一次，再分配到实际物料；真实退货累计回冲，不超冲、不丢尾分。
- 开单与配置修改共用套餐主档锁；开单使用 READ_COMMITTED，报价指纹同时检查价格与组成。商品停用、销售单位失效、报价过期和库存不足均拒绝整单。
- 单品验收：`docs/reviews/2026-10-12-价格体系收口验收.md`；套餐及最新验证：`docs/reviews/2026-10-13-套餐独立定价验收.md`。

## 已确认问题

### P0


- 外部支付仍未真正接入微信/支付宝网关。
  现状：`payment-intent`、`payment-confirmation`、公开回调入口和幂等落库已经有了，但还没有真正生成平台支付参数，也没有完成回调验签。客户端自行确认入口已由 `payment.client-confirm.enabled` 默认关闭，只在本地联调显式开启。
  风险：当前链路只适合联调和本地开发，不能当成正式收款方案上线；公开回调入口在验签落地前同样不可对外暴露。

- 外部支付失败补偿和对账闭环还没完成。
  现状：支付成功路径已拆开，但支付超时、重复通知、补单、对账差异等异常场景还没有系统化处理。
  风险：后续一旦接真实支付，会出现“用户已付款但订单未完成”或“重复确认”的运维成本。

### P1

- 支付编码说明仍未在所有文档和初始化脚本中同步。
  现状：核心 Java/前端代码已统一，但旧迁移、旧 README、部分历史注释还保留旧口径。

- Web 端仍有少量业务页面残留“可打开但细节未完全收口”的问题。
 现状：高频页面的权限与主流程已基本收口，但仍需继续排查库存、POS、订单、客户等页面里的占位交互、快捷操作和边缘态表现。

- 绩效规则类别的业务语义不是完全对称。
  现状：销售提成按商品、套餐提成按套餐；充值提成和拉新提成目前没有目标对象维度；品牌推广只有类别定义，没有实际结算事件链路。
  风险：如果后续继续按“所有类别都能绑定 targetId”去扩展页面或接口，会再次做出看起来能配、实际不生效的伪闭环。

## 架构判断

- 分层方向是合理的：`core-domain`、`core-application`、`core-infrastructure`、`api-admin`、`api-client`、`admin-web`。
- 当前实现还不是严格分层。
  现状：`core-application` 直接依赖 `core-infrastructure`，并直接使用基础设施实现类、Mapper、`JdbcTemplate`。
- 结论：短期可以继续开发，但中期需要做边界收敛，否则维护成本会越来越高。
