# 当前开发状态

最后更新：2026-10-13

## 用途

这份文档只记录当前仍然有效的开发事实，供后续每次继续开发时快速对齐。
不要把历史交付文档当成当前状态，历史资料仅用于追溯背景。

## 当前判断

- 项目已不是早期骨架，后端主业务模块、管理端页面、数据库迁移都已落下较多内容。
- 业务覆盖范围已经超出“农资进销存”，实际是“交易 + 会员 + 营销 + 售后 + 赊销 + 绩效”的门店经营系统。
- 当前更像“主体功能已铺开，但关键闭环和安全性还未收口”，不适合继续无节制加模块。

## 当前库存结构（已统一）

- 收货批次、批次货位余额与移动流水组成唯一库存账；采购、销售、退货、盘点、调拨全部接入。
- 没有按 SKU 激活或选择 LEGACY/BATCH_LOCATION 的运行分支；旧表仅保留历史。
- 库存快照统一显示商品主单位，账本使用持久基准单位。新建商品同时建立单位，新建门店同时建立默认后仓。
- POS 和线上支付实际扣减库存并记录订单行批次成本；提货只核对出库证据，不重复扣减，多批次可逐项确认。
- 退货恢复原批次，使用 current read 防并发超退；盘点/调拨/收货防重复提交。
- MyBatis 与 JDBC 共用 Flex 数据源及事务连接，不能直接把 Boot 原始 Hikari 数据源接到写库存的 JDBC 服务。
- 源码最新迁移 V131，共87份SQL/Java迁移；V131 增加套餐成交快照及分摊单价精度。
- 本机开发库已获用户明确授权备份并重建，并实际升级至V131（87份迁移成功、失败0）。旧测试数据备份在 `.local-backups/`，不进入Git。当前只有默认门店、后仓与管理员，无旧业务商品和订单。
- 当前运行说明：`docs/runbooks/retail-fact-chain-rollout.md`；验收：`docs/reviews/2026-10-12-库存统一修复验收.md`。
- 2026-09 的切换/灰度计划已被本次决策替代，不再按这些计划启用商品或回退库存。

## 当前价格结构（已收口）

- 档案价格均明确为元/持久化基准单位；零售价必备，会员价与最低价可选，0代表未启用。所有销售单位按持久化系数换算，不区分门店、渠道、会员等级或日期策略。
- VIP 有效性由 customerId 对应的客户档案决定；过期会员按零售价，会员价不能低于最低价。
- 商品多维策略只读，单独线上价不再维护。最低价只用于提醒/议价授权，不参与售价兜底。
- 单价议价与整单手工优惠共用 `order:price:override`，默认只授予超管。其他角色可通过现有角色管理明确授予；正常收银无需此权限。
- 议价记录保存标准价、成交价、原因及员工。整单优惠金额与原因保存到订单；历史成交价不会随商品调价改变。
- 收银展示报价与结算报价不一致时要求重新报价；报价失败整体拒单。前端异步报价不能恢复已删除商品，恢复挂单在标准价未变化时保留已谈成交价。
- V130 精确转换旧价格的计价单位，不改采购成本或历史订单；不能精确换算或价格冲突时迁移停止，不能猜价。
- 用户已明确把套餐独立定价纳入本轮。门店 POS 按套餐元/套价格收款，前端保留一行套餐，物料由后端展开；物料正常零售价只用作分摊权重，不覆盖独立套餐价。
- 套餐组、名称、套数、每套成交价随实际物料订单行保存；total_price 为按分分摊后的权威金额，unit_price 可保留12位参考精度。历史套餐行不猜测回填。
- 含套餐订单退货按原实付分配净金额，分次退货使用累计数量并结清尾分；0元物料仍回库并保留事实。直接退款与售后共用现有售后事实，重复/超退受订单锁约束。
- 套餐固定提成按实际套数计算一次，再分配到实际物料；真实退货累计回冲，不超冲、不丢尾分。
- 开单与配置修改共用套餐主档锁；开单使用 READ_COMMITTED，报价指纹同时检查价格与组成。商品停用、销售单位失效、报价过期和库存不足均拒绝整单。
- 单品验收：`docs/reviews/2026-10-12-价格体系收口验收.md`；套餐及最新验证：`docs/reviews/2026-10-13-套餐独立定价验收.md`。

## 已确认问题

### P0

- 门店赊销退货尚未形成系统内闭环。
  2026-10-13源码核对：售后与退款服务均拒绝纯赊销退货；混合支付退款没有赊销冲应收分支。下一轮需要让实物回库、未还欠款冲减、已收款退款及原单追溯一致，不能要求员工另做线下冲账后继续留下原欠款。依据：`AfterSalesApplicationService.createFromAdmin`、`OrderPaymentService.refund`。

- 门店POS开单后人工配送尚未接通。
  2026-10-13源码核对：POS开单固定已完成，开单命令没有配送/收货信息，派单只接受待发货订单。现有配送能力主要服务客户配送订单，不能把它当作店员开单送货已交付。自动收货还只更新订单，没有同步配送签收及订单完成事件；下一轮需统一履约完成入口与幂等。依据：`OrderApplicationService.createPOSOrder/shipOrder/confirmReceipt`、`OrderAutoFinishJob.autoFinishOrders`。

- 外部支付仍未真正接入微信/支付宝网关。
  现状：`payment-intent`、`payment-confirmation`、公开回调入口和幂等落库已经有了，但还没有真正生成平台支付参数，也没有完成回调验签。客户端自行确认入口已由 `payment.client-confirm.enabled` 默认关闭，只在本地联调显式开启。
  风险：当前链路只适合联调和本地开发，不能当成正式收款方案上线；公开回调入口在验签落地前同样不可对外暴露。

- 外部支付失败补偿和对账闭环还没完成。
  现状：支付成功路径已拆开，但支付超时、重复通知、补单、对账差异等异常场景还没有系统化处理。
  风险：后续一旦接真实支付，会出现“用户已付款但订单未完成”或“重复确认”的运维成本。

### P1

  现状：核心 Java/前端代码已统一，但旧迁移、旧 README、部分历史注释还保留旧口径。

  风险：如果后续继续按“所有类别都能绑定 targetId”去扩展页面或接口，会再次做出看起来能配、实际不生效的伪闭环。

### P2

- 前端现在已按权限动态注册业务路由，菜单展示和默认落点也会读取后端当前员工菜单树；但数据库菜单路径仍有部分历史数据尚待迁移生效，当前仍保留少量兼容 alias。
- 调拨现在已有正式主单与批次审计明细，但仍是“一次提交即完成”的直达模型，还没有审批、在途、签收等更细状态流转。

## 架构判断

- 分层方向是合理的：`core-domain`、`core-application`、`core-infrastructure`、`api-admin`、`api-client`、`admin-web`。
- 当前实现还不是严格分层。
  现状：`core-application` 直接依赖 `core-infrastructure`，并直接使用基础设施实现类、Mapper、`JdbcTemplate`。
- 结论：短期可以继续开发，但中期需要做边界收敛，否则维护成本会越来越高。

## 接下来的开发顺序

### 2026-10-13已授权实施顺序

库存统一、单品价格和POS套餐独立定价已验收。下一轮优先完成已确认的小门店MVP：收款/赊销、真实物料、人工配送和退货，暂不扩展营销、会员等级定价或供应链模块。

1. 库存、价格及套餐基线复核完成，另已修POS券加钱包重复扣款、现金/混合加券拒单、无效支付明细、钱包来源流水及授权、券并发核销；正在固化本地可回退版本。
2. 优先补齐赊销销售→部分还款→退货冲欠款/退已收款→对账；覆盖纯赊销、混合支付、已部分还款和已还清后退货，不允许现金退款与应收重复冲减。
3. 接通店员POS录单→待配送→人工派单→签收；复用现有配送单与库存事实，配送/签收不再次出库，完成事件只执行一次。
4. 同轮修复角色保存绕过菜单授权权限的问题，再分别以老板、收银、库管身份做真实浏览器全流程验收。
5. 从业务页面建立样例，执行采购、分次收货、单品/套餐混卖、线下实际收款登记、赊销、还款、提货/配送和退货；日终库存流水、实收、退款和客户欠款必须一致。自动化通过不能替代这项员工实操验收。
6. 门店闭环通过后，在商户资质及回调环境具备时接真实微信/支付宝网关、验签、异常补偿及对账。最后再做应用层与基础设施边界整理。

建议验收结果：欠款100元、按原成交口径退货30元时，应收余70元且物料回原批次；已部分还款或已还清的订单，需要结合实际收款与原还款记录计算应收冲减和现金退款，不能从支付方式标签猜金额。

`docs/superpowers/plans/2026-09-28-system-closure-plan.md` 保留为历史计划；下一轮以当前经营范围、已验证结果和上述新确认断点确定顺序，开工前再细化影响范围与验收规则。
