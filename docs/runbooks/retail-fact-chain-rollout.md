# 统一库存账运行说明

更新：2026-10-17。此前的 SKU 灰度启用、双模式与回滚到旧库存方案已撤销。系统尚未正式上线，当前只运行一套库存账。

## 唯一库存来源

- `inventory_receipt_batch` 保存批次来源、单位、数量、成本与已有日期。
- `inventory_batch_balance` 保存批次在货位上的基准单位余额。
- `inventory_movement` 保存收货、销售、退货、盘点与调拨流水，只追加不修改。
- `inventory.quantity` 是余额汇总后的**商品主单位**展示值，不是另一套库存。
- `order_item_batch_allocation` 保存订单行实际扣减的批次、货位、数量与成本。

`inventory_batch` 与旧流水保留历史；`inventory_balance_feature_status` 不再参与任何运行路径。不需要为商品激活或选择模式，也不能用它切回另一库存来源。

## 作业规则

采购列表的“入库”进入统一收货页，支持多采购行、多实际批次和分次收货。收货、余额、流水、采购状态必须在同一事务内提交。一次请求沿用同一个 `requestKey`；重试已处理请求会被拒绝，不会重复增加库存。

销售按有效期优先分配可用库存，排除过期、预留以及停用货位；库存不足时整笔订单回滚。线上支付完成与 POS 共用出库入口，出库必须带订单明细 ID。套餐按后端确认的独立每套价格成交，并展开为实际物料行；库存仍按这些物料的真实销售单位扣减，没有套餐库存表。完成提货只核对已出库批次，不再次扣库存。多批次提货逐批勾选后一次完整确认。确认前若已退部分，只核对原SALE扣除同分配RETURN后仍需交付的批次和数量；原申请与原销售量不改。已全退批次不用再勾选，全部退回时保留待办并显示阻断原因，不能伪造已交货。已完成请求重放不重复交货，完成列表不按后续退货猜历史交付量。

退货关联原订单行，按成交时的数量比例回到原批次、原货位并沿用原成本。含套餐订单的可退金额按原实付分配，累计数量计算退款尾分；本次可退0元的套餐物料仍须记录数量并回库。累计退货不能超过实际售出数量；重复请求和超量退货都回滚。已回库物料不得重复交付；提货及配送遇售后申请/待退款暂停，部分退货完成后可交剩余实出库物料，保留原退款状态，全退/取消停止新的交付。

盘点提交账面数量、实盘单位和数量、原因及 `requestKey`；差异由后端按真实基准余额计算。提交期间库存发生变化时需要刷新并重新盘点，不能继续套用旧差异。跨店调拨提交实际单位和数量，不能在前端先换算成小数箱数；后端自动建立目标批次并保留来源批号、日期和成本，出入两端一并提交。

只有有效期、只有生产日期或日期都未知均可以按真实信息记录，不补造日期；两日期都存在时生产日期不能晚于有效期。有效期一旦明确，就参与过期判断和批次分配。

## 只读对账

```bash
scripts/verify-retail-fact-chain.sh --database agri_system
```

脚本接受 `MYSQL_PWD` 环境变量，不需要在命令行写密码。可用 `--stores`、`--products` 缩小检查范围，但所有商品使用同一规则。

- L1：基准余额换算为主单位后，应等于库存展示值。
- L2：每个批次货位余额应等于全部流水净额，包含收货流水；不再另外加一次收货数量。
- L3：销售分配应对应实际销售出库，批次、货位、数量与成本一致。

退出码 0 表示一致，1 表示存在差异，2 表示参数或查询失败。发现差异应追查业务单据，不能直接覆盖余额或删除流水。

## 人工配送

POS结算选择整单门店配送并填写收货人、电话和地址，收款/挂账与出库仍发生在开单时，进入待派送。订单页按真实配送状态派本店在职员工，实际交给收货人后人工确认签收。签收不再次出库、收款或记POS提成；部分退货后的剩余配送仍保留订单部分退款状态。

线上订单预览不推进履约；实际支付完成后才进入待派。首次签收前退货不提前扣其它订单的客户累计，首次签收按已完成退货补齐净额、积分和提成。未知历史记录不能猜补。工作台净销售包含赊销，不能拿来与现金抽屉直接对等；按收款来源、退款和剩余欠款核对。


## POS异常恢复（V133，2026-10-21）

新管理端POS请求必须带安全UUID requestKey，先在本机保存核对摘要再发送。PosSaleSubmissionService按唯一请求行锁包原开单事务；成功结果与订单、钱货同时提交。核对GET返回UNKNOWN不能代表失败；POST取消必须插入/锁同一身份并提交CANCELLED，迟到请求才不能成交。若原请求已成功，取消返回COMPLETED，须核对原订单，不得新收。明确业务拒绝也先取得后台取消确认才能解冻；原钱包验证码仍在数据库条件UPDATE一次性核销，不再用Controller临时Redis锁抢先拒绝同请求重放。

V133只增加pos_sale_submission请求事实表，不回填旧请求号。前后端配套发布；请求表、成功记录和取消屏障不得因退款或清理缓存删除。旧无请求号的本机记录只能人工核对，不自动推断未成交。当前仅3092隔离环境升级V133，89份迁移；其他旧预览/API与开发库未升级。本轮验证见 `docs/reviews/2026-10-21-POS异常恢复验收.md`。
