# 员工签收异常恢复验收

## 问题与改动范围

原配送签收页只在内存保存原confirmationKey，onShow清空未知状态。丢响应后隐藏或销毁重进，遇改派/退货导致新指纹时，可能重新确认变化后的交付内容。

本轮只修改mini-staff配送详情与其页面生命周期测试，不改后端、权限、数据库、钱货或已完成订单，不部署到现有预览。

沿现有提货页的有限本机记录方案，POST之前保存并回读原确认标识，键按真实员工、门店和订单隔离；不保存令牌、地址、电话及商品清单。结果未知仍核对同一订单，不自动接受新的确认标识。原标识相同且逐项重新核对后可人工重试。

本机读写失败、损坏、替换或清理失败继续冻结；首次明确拒绝可清原记录，未知后的拒绝不能抹掉未知。已收到合法签收完成响应或读取原任务完成事实后，仅清理匹配的原记录；清理失败仍提示核对。

## 失败复现与修复

- 实际编译生产SFC执行onLoad/onShow/onHide：隐藏重进、页面销毁重建、请求挂起离页、写失败及完成后删失败等用例先失败，再修复通过。
- 追加会话切换期间旧拒绝响应：RED显示旧响应清掉原记录；catch改为完整当前会话/页面代次守卫后通过。
- 独立审查发现同scope合法JSON替换：RED显示第二次提交变化后的key。恢复时保留内存原key作一致性校验，失配后持续冻结，连续隐藏重进也不能接受替代key。

## 验证结果与边界

- 配送页面定向19项通过；员工端完整66项通过，零失败、零跳过。
- 共享契约51项通过；员工端类型检查、微信生产构建通过。构建输出临时目录，不覆盖当前开发者工具工程。
- 本次为真实SFC逻辑及生命周期自动测试，API/存储故障使用边界替身；不是手机网络故障注入、真实微信杀进程或新业务订单验收。
- 本机记录用于防误操作，不是防篡改签名。全新进程不能独立证明一份格式合法且scope相同的本机记录在启动前是否被人为替换；后端身份、权限、原订单状态及确认指纹仍是实际写入边界。不宣称可防用户清除全部本机数据。
- 本轮未重跑后端871项和管理端276项，原数字仅为前轮记录。
