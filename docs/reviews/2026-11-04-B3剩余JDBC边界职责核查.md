## 文件一：JdbcAccessConfig.java（44 行，0 处业务 SQL）

- **事实**：只定义两个 Bean——`JdbcTemplate` 绑定 Flex 数据源
  （保证 JDBC 与 MyBatis 走同一事务连接，见 `JdbcAccessConfig.java:22-24`）；
  `FlexTransactionManager` 重写 `doBegin` 把显式隔离级别应用到真实 Flex 连接
  （`:28-43`，失败时回滚并抛 `CannotCreateTransactionException`）。
- **判断**：必要连接适配，不是债务。AGENTS.md 明确要求「保留当前事务适配与异常清理，
  不能只写注解或切回 Boot 原始数据源」。
- **结论**：**保留**。无提取动作。

## 文件二：InventoryLedgerService.java（360 行，13 处 jdbc 调用）

- **事实**：库存账本核心写入路径。调用点分类：
  - 锁读：`:227` 盘点前账面 `SELECT quantity FROM inventory ... FOR UPDATE`；
    `:232` 批次余额 `FOR UPDATE`；`:148` 退货累计 `FOR UPDATE`。
  - 幂等：`:143,243` `idempotency_key` COUNT 防重（收货/盘点）。
  - FEFO/聚合：`:294,312,319,355` 批次选择、批次汇总、收货行回查。
  - 写入：`:103` `UPDATE order_item SET cost_price_snapshot`（出库后成本快照，
    与 `costs.refreshOrderItemSnapshot` 同段）。
  - 一致性校验读：`:73,130` 订单门店归属。
- **锁链路核清（本次核查的关键证据）**：所有库存写入入口（销售 `:78`、退货 `:132`、
  盘点 `:223`、调拨 `:264`）统一先走 `balances.lockStock(storeId, productId)` →
  `BatchBalanceService.lockStock`（core-domain `BatchBalanceService.java:136`）→
  `InventoryRepository.findByStoreAndProductForUpdate` → `InventoryMapper.java:31`
  （MyBatis `SELECT * FROM inventory ... FOR UPDATE`）。`:227` 的 JDBC FOR UPDATE
  锁的是**同一张 `inventory` 表的同一行、同一 Flex 事务连接**，即同一把行锁在
  同一事务内的再次获取，不是第二把锁。
  - 这证实 B1 的修正结论：不存在「两套账、两把锁、锁序反转」的实证；
    MyBatis 与 JDBC 混用是刻意共用同一锁行 + 同一事务连接的设计。
- **判断**：13 处 JDBC 属钱货事实命脉（锁、幂等、FEFO、成本快照）。提取为 Mapper
  接口只带来分层纯净，需重写核心写入路径并全量重验锁序/事务，风险收益比不成立。
- **结论**：**保留现状**。与 B1 一致：仅在出现具体一致性缺陷证据时按调用点小步收敛，
  不为去裸 SQL 而改。`inventory` 旧汇总表仍是统一的库存行锁载体与盘点账面对照，
  `quantity` 由 V129 迁移回填、E2E 断言覆盖，不在本记录处理其存废。

## 文件三：PickupFulfillmentService.java（415 行，2 处 jdbc 只读查询）

- **事实**：
  - `:177` 按 `batch.baseUnitId + productId + is_base_unit=1` 查基准单位名
    （工作项分配行循环内逐行查；提货工作项行数少，非高频 N+1）。
  - `:312` 一次批查移动事实 + 售后处理中标记（`IN` 占位符拼接，
    提货证据链核心 SQL：SALE 事实、RETURN 累计、`processing_after_sales` 派生列）。
- **判断**：两处均可按既有模式（`TransferRecordQuery`/`PickupTaskQuery`/
  `AssignedDeliveryTaskQuery`）提取为领域查询接口 + infra 唯一实现。但 `:312`
  是提货交付资格证据链，属于钱货安全边界；提取须真实 SQL 基线改前改后比对 +
  完整后端回归 + 独立静态审查，是独立子项的工作量，不应在评估记录里顺手完成。
  `:177` 收益更小（仅分层纯净）。
- **结论**：**可提取但未实施**，留作独立子项，前置条件：SQL 文本逐字一致、
  preview/confirm 证据链行为不变。若后续实施，建议与 `PickupTaskQuery` 一并评审
  是否合并为提货域统一查询对象，而不是新增第三个平行接口。
