# 钱包授权码仓储边界

## 范围与方案

清单B3剩余四个JdbcTemplate涉及文件中，WalletApplicationService用JDBC直接生成授权码及执行旧关联；核销、查询则已经经过WalletAuthCodeRepository。本轮基线3702bc7。只把两段原SQL归入已有仓储，不改钱包金额、授权、日志与事务，不新增表、模式或第二事实来源；库存账、提货、事务适配另按真实职责审查。

实施顺序：先将原隐私SQL测试移至可同时依赖应用/基础设施的api-admin测试模块，跑原两项基线；增加真实Flex事务中发放→原Mapper核销→重复拒绝→伴随写入→整体回滚基线；然后原SQL迁移、同测试复验，完整后端和独立静态审查。

## 改动

- WalletAuthCodeRepository补insertIssuedCode与associateConsumedCode两个明确原写入动作，唯一基础设施实现保留原INSERT/UPDATE全文和参数次序、status=1、Timestamp转换及受影响行数。
- 应用服务去JdbcTemplate，仅调用已有授权码仓储。SecureRandom六位码、空金额转0、缺省五分钟、同一now生成expiry、空关联参数短路、日志不含原码保持；公开入口事务注解不变。
- 原通用save方法保持兼容，但发放使用明确插入动作，避免改用通用mapper.save时增加字段、更新时间或空值处理差异；操作仍针对同一个wallet_auth_code表。没有新数据库、独立事务或新连接池。
- 原隐私两用例迁到api-admin，生成仍通过真实JdbcTemplate/H2读取数据库，不退化为仅mock仓储；关联成功/失败日志仍按原两个影响行数验证。新增混合JDBC/MyBatis的Flex回滚用例。
