# 小程序端方向判断与下一步执行清单

日期：2026-11-07
性质：**只读盘点 + 基线实跑，未改任何生产代码、DDL、数据**。
问题：用户问「继续做小程序端，是不是应该先做员工端」。

---

## 一、结论：是，先做员工端（且这本来就是既有决策）

| # | 依据 | 证据 |
|---|---|---|
| 1 | **既有设计决策已定顺序** | `docs/superpowers/specs/2026-10-29-双端小程序-调研与总体决策.md:105`：「员工端不收客户线上款时可先做任务与扫码，不必等客户支付联调完」「真实支付未就绪前，客户端不能展示可完成的微信支付或把意图当到账」 |
| 2 | **符合项目最高优先级** | `AGENTS.md`：优先完成小规模农资门店的采购、库存、销售、赊销和人工配送闭环。员工端 12 页直接服务扫码查货、分次收货、本人配送、库房提货；C 端商城是增量渠道 |
| 3 | **完成度与成本** | 员工端 `mini-staff` 已有 12 页、6 类写入口、71 项自动测试、微信模拟器联调通过；C 端 `mini-customer/` **工程不存在**，`api-client` 无商品目录/订单列表接口，真实支付未接 |
| 4 | **风险与资质** | C 端被主体认证、商户号绑定、备案域名、种子/农药网售类目、平台验签/查单/退款/对账卡住（决策 `:98-102`）；员工端是内部用户、不收线上款，出问题可控 |

**但要点醒一个现实**：员工端**代码侧已基本收口**，下一步的瓶颈不是「再写几个页面」，
而是①真机验收所需的**真实 AppID + 手机可达 HTTPS 服务**（外部条件，代码补不了），
②**E6 移动销售**这个尚未开放的大工程（涉及钱货写入，需单独授权）。

## 三、三条可执行路径

### P1 · E6 移动销售（员工代客开单 / 手机收银）
- **价值**：把门店销售闭环从电脑 POS 延伸到手机，是 AGENTS.md 优先级里最大的功能缺口。
- **代价**：需开放后端销售写入口给移动端，牵动报价、库存扣减、收款/挂账、请求幂等（V133 模式）、
  权限与结果恢复；属**钱货核心**，必须独立一轮、先说明影响范围并单独授权。
- **验证**：真实 MySQL 全链、重复提交/断网恢复、权限与门店隔离、完整后端回归 + 员工端 71 项。

### P2 · E4 收尾 + 真机验收前置（**推荐，低风险**）
- 内容：①改派后手机端旧任务的明确拒绝与冻结（`2026-11-01-配送明确改派实施进度.md` 仍列「手机旧任务拒绝」待补）；
  ②员工端三处结果未知恢复边界补强（签收/提货/收货已有基础，可补真实 watch/会话并发用例）；
  ③产出**真机验收清单与可复现步骤**（AppID、HTTPS、权限拒绝、弱网、杀进程、存储可靠性），
  等账号到位即可按单执行。
- **代价**：只动 `mini-staff` / `mobile-contracts` 源码与测试，**不碰后端钱货、不需要 AppID、零 DDL**。
- **验证**：员工端 71+ 项、共享包 51 项、类型检查、微信生产构建；真机部分只出清单不冒称验收。

### P3 · C 端只读地基（不推荐现在做）
- 内容：建 `mini-customer/` 骨架 + `GET /api/client/catalog/products` 等只读目录 DTO/接口，**不碰支付**。
- **判断**：技术上可行且能绕开支付资质，但它违背「先员工端」的既有决策，
  且会在员工端真机未验、E6 未做时分散投入；评估报告 `:23` 提醒「最大风险是在未收口的工程结构上继续叠加商城」。

## 四、建议

**先走 P2**：它是唯一「不依赖外部资质、不碰钱货、可自动验证」的路径，
同时把真机验收准备做扎实，等 AppID 到位可直接闭环。
P1 价值最高但需要你明确授权销售写入范围；P3 建议等 P1 与真机验收完成后再启动。

## 验证边界

本轮为只读盘点与基线实跑，未改代码/数据/DDL；所有完成度判断来自源码与验收文档，
未做真机、微信开发者工具或浏览器实操，不把模拟器联调当成手机验收。
