# 库存口径与员工端范围确认，及下一步排期

日期：2026-11-08
前置：`2026-11-08-移动开单选客户选商品与结算履约核对.md`

## 一、需求确认

### 需求 A：商品清单与库存逻辑应与后台一致，即按门店维度判断库存

**确认：成立。但要拆成两件事——一件已经做到，一件还没做。**

| 子项 | 现状 | 结论 |
| --- | --- | --- |
| A1 门店维度隔离库存 | 已实现，见第二节证据 | **不需要改造**，补测试防回归即可 |
| A2 库存数量的计算口径 | 后台列表与员工端都读 `inventory` 投影；真正扣减读批次账 | **这是要做的实质工作** |

补充一条容易误判的点：**商品清单本身不按门店过滤是对的**。`product` 是全局主数据（表里没有 `store_id`），后台「商品管理」也不分门店；按门店区分的只能是"这个商品在本店有多少可售"。若业务要的是"某门店不上架某商品"，那是**门店商品上下架**这个新能力，当前后台也没有，不建议现在加——它牵涉价格、套餐、采购与报表，属于另一个量级。

### 需求 B：员工端不开放快速建档，仅保留在后台

**确认：采纳，本项不再讨论。**

落地方式（都是减法）：

- 不新增 `POST /pos/customers` 之类写接口，`PosCatalogController` 保持只读。
- 移动端在"搜不到客户"时给引导，而不是给创建入口：「没有找到客户？请联系后台建档；或按散客开单（散客不支持配送）」。
- 把"员工端不写客户主数据"写进权限边界说明，避免以后被当成遗漏补上。

代价要说清楚：客户不在档案里，员工就**无法开配送单**（当场交货仍可按散客开）。这是有意的取舍——客户主数据的质量比员工少跑一趟更重要，重复建档造成的重号客户后续要合并，成本远高于一次后台录入。

## 二、门店维度：已经是通的（证据）

1. `inventory` 实测结构是 `(store_id, product_id) → quantity`，唯一键只有这两列（`SHOW COLUMNS FROM inventory` 无 `batch_no`），即"一店一商品一行"的投影，不存在同商品多行的重复。
2. 员工端读库存时**请求可以不带 `storeId`**，后端 `PosCatalogApplicationService.scopedStore(null)` 直接取 `CurrentUser.storeId()`；非管理员传别店会抛「不能读取其他门店库存」。也就是说**客户端无法越权看别店库存**。
3. 下单扣减用订单门店（`staff.storeId` → `order.store_id`），`InventoryLedgerService.outbound` 还额外校验「出库门店与订单不一致」；E2E 断言都是 `WHERE store_id=?`。
4. 后台库存列表按 `InventoryQuery.storeId` 过滤；不传则是"全商品跨门店"视角——这是后台应有的能力，移动端不复制。

## 三、真正不一致的是"数量口径"

| 用途 | 读的是什么 | 口径细节 |
| --- | --- | --- |
| 后台库存列表 `findPage` | `inventory.quantity` | 商品 LEFT JOIN inventory，仅按门店过滤 |
| 员工端库存展示 `/pos/catalog/inventory` | `inventory.quantity` | 同上（同一服务） |
| 出库/扣减 `InventoryLedgerService.select` | `inventory_batch_balance` | `base_quantity - reserved_base_quantity`，且排除过期批次、停用货位 |

偏差来自三处，都会让"展示值 > 实际可售"：

1. **预留**：`reserved_base_quantity > 0`（下单占用、调拨占用）
2. **过期批次**：`inventory_receipt_batch.expiry_date < CURRENT_DATE`
3. **停用货位**：`inventory_location.status <> 1`

开发库当前这三项都是 0 / 空，所以实测两个口径恰好相等（93 / 60 / 40），`inventory` 与批次余额完全对齐。**这是假象**：上线后一旦出现预留或过期批次，员工端会显示 100 却只能卖 80。

补充一条同类问题：`validateSaleQuantity(productId, unitName, quantity)` **只校验单位与数量格式，不查库存**，库存不足要到出库 `select()` 才抛「可用库存不足，已排除预留及不可销售批次」。事务会回滚、不会错账，但用户是**提交之后**才看到失败。

## 四、整改方案

### P0-1 商品目录直接带"本店可售量"（推荐）

后端：

- 新增一个只读聚合查询：按 `(storeId, productIds)` 对 `inventory_batch_balance` 求和，条件与 `select()` **逐字一致**（货位 `status=1`、未过期、扣预留）。放在 `core-domain` 的库存仓储端口上，infra 实现，避免应用层再写 SQL。
- `PosCatalogApplicationService.products()` 对当前页商品批量查一次（≤ pageSize），回填 `availableQuantity`（基准单位）。**不做 N+1**。
- 移动端删掉 `readStock` 那次 500 行的 `inventory` 全量拉取——现在它只为了显示一个数字，还带着错误口径。

移动端：

- 商品行显示「编码 · 本店可售 N」+「¥xx/基准单位」。
- `N <= 0`：行置灰，点击提示「本店无可售库存，请先在后台收货或调拨」，**禁止加入购物车**（比"允许加入、提交时失败"体验好，也避免用户反复试）。
- 有货才可加入；文案始终保留"以出库为准"，因为可售量是查询时点的值。

取舍（必须写在文档里，避免以后被当成 bug）：

- 可售量是**查询时点**快照，并发下仍可能被别的收银员买走，**出库校验永远是最终裁决**，不能因为展示了库存就省掉它。
- 不做跨店库存展示（员工无权限，也不该引导他们去别店拿货）。
- 不引入"预留"给移动端：员工端不锁库存，锁库存是调拨/线上订单的事。

### P0-2 数量预检（建议只做前端本地比，不加接口）

`validateSaleQuantity` 不查库存这件事，**不建议**顺带加库存在里面：那会让"校验方法"变成"查库存方法"，而且校验与出库之间仍有窗口。更划算的是数量面板确认时用已拿到的 `availableQuantity` 本地比一次，超了就地提示并给出上限。

### P0-3 权限落地（阻塞"能不能用"）

`pos:order:create` 目前只有 SUPER_ADMIN（V59）。两个选项：

- (a) 文档化后台勾选步骤，写到 `docs/runbooks`，零代码风险，但要人工配；
- (b) 新增迁移给店长角色默认授权，需要业务先确定角色定义。

**建议先 (a)**：角色体系还没定，用迁移固化默认授权，后面调整要再写迁移，不如等角色定稿再一次性做。

### P1 其它模块

1. **我的订单（只读）**：员工开完单只能看到订单号，回看不到"今天开了几单、哪单还没送到"。接口 `GET /pos/orders?mine=true&date=`，按 `staff_id`/`store_id` 隔离，只读投影不含资金细节。
2. **门店配送单与配送任务是否两套（先调研）**：POS 门店配送单落 `order_status=4` + `order_delivery`，而员工端已有「本人配送」页走 `assigned-deliveries`。这两条链路是否同一批数据、POS 配送单会不会进配送员视野，**必须先核查再谈开发**，否则可能造重复功能。
3. **退货/退款**：涉钱货回写，需单独授权，P2。
4. **余额/混合支付**：需钱包授权码 UI 与资金权限，P2。
5. **真机验收与发布**：外部资质（正式 AppID、备案域名、HTTPS），并行推进，不阻塞开发。

### 明确不做（防止范围膨胀）

员工端客户建档、商品维护、库存调整/盘点、跨店调拨申请、赊销、优惠券/专用金/人工改价。这些留在后台或已按你的要求移除。

## 五、排期建议（按依赖顺序）

| 顺序 | 内容 | 前置 | 验收 |
| --- | --- | --- | --- |
| 1 | P0-1 目录带本店可售量（后端聚合 + 字段 + 移动端替换 + 禁止 0 库存加购） | 无 | 构造预留/过期/停用货位三种数据各一条用例，展示值必须等于出库可售量；模拟器复验 |
| 2 | P0-3 权限 runbook + "客户不存在"引导文案 | 无 | 非 SUPER_ADMIN 账号实测开单成功；契约与页面测试 |
| 3 | P1-2 配送链路调研（只读核查，出结论） | 无 | 一份结论，明确是否两套，再决定是否开发 |
| 4 | P1-1 我的订单 | 1 完成 | 只读、按员工隔离、看不到别店/别人员工单 |
| 5 | 退货、余额/混合支付 | 单独授权 | 另开文档 |

第 1 步建议**本轮就做**：它是"一致"这条承诺的兑现，且改动集中在只读投影层，不碰钱货写入，风险最低。

## 六、开始前需要你拍板的三件事

1. **后台库存列表是否同批改为可售量**（我建议同批改，但作为独立提交；否则后台与员工端又分叉）。
2. **0 可售是否禁止加入购物车**（我建议禁止 + 明确提示，而不是允许到提交才失败）。
3. **权限先文档化还是加迁移默认授权**（我建议先文档化）。
