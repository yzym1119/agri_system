# 员工端整单多货清单实现（手册 V2.1 ③ 前半：按原订单聚合）

日期：2026-11-08　分支：`codex/staff-unified-review`（父提交 `ab3f8ea`）

## 本轮要解决的问题

手册 V2.1「多货待办与库房交付」要求：**待取列表按原订单聚合展示，主信息为客户/原单、待交商品项数和剩余数量**，并明确「当前底层任务按原请求存在，聚合仅为视图，不另建第二套订单/库存」。

改造前手机列表是**按提货请求**一行一条（`order_pickup_request` 一条 = 一个订单明细 = 一个商品），一单三货到库房就是三张互不相干的卡，且：

1. 卡上只有 `orderNo + productName`，**没有剩余可交数量**，库管仍要逐条点进去看；
2. **没有整单口径**：交完第一项后，列表里已交项直接消失，看起来像整单完成了；
3. **没有客户**，无法在库房交付时认人。

## 一个不能省的前置核查：MySQL 不允许 `IN` 子查询带 `LIMIT`

第一版 SQL 直接写了 `WHERE r.order_id IN (SELECT DISTINCT ... ORDER BY ... LIMIT 21)`，H2（`MODE=MySQL`）跑通、5 项单测全绿，但在本机真实 MySQL 9.6.0 上实测报错：

```
ERROR 1235 (42000): This version of MySQL doesn't yet support 'LIMIT & IN/ALL/ANY/SOME subquery'
```

改为派生表分页（`FROM (SELECT DISTINCT ... ORDER BY ... LIMIT 21) paged JOIN ...`）后，同一条 SQL 实体库执行通过（无数据时返回 0 行，无语法错）。**这也说明 H2 通过不等于 MySQL 通过**，凡是 H2 里过了的方言特性都要在实体库再验一次。

## 方案与取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 聚合位置 | 后端按订单分页 + 分组 | 前端按 `orderNo` 聚合会被分页切断（同一订单的请求可能落在两页），从而把「还有 2 项待交」算成「整单已交完」，正是手册禁止的错误 |
| 剩余数量来源 | 复用 `PickupFulfillmentService` 现有装配 | 「已出库量 − 同分配正数 RETURN」是唯一余量口径。若在列表里另写 SQL 算余量，就是第二套库存/余量事实 |
| 装配范围 | 新增 `listPickupRequestsForOrders(storeId, orderIds)`，抽出原 `assemble()` | 只缩小取数范围，不复制暂停/阻断/摘要判断；一页最多 20 个订单，不按整店拉取 |
| 客户信息 | 只给脱敏称谓（`张**`／`散客`） | 原列表刻意不含客户（`PickupTaskQuery` 注释：「不含客户、金额、成本」）。手册要「认人」，最小加宽度是姓名首字 + 星号；手机号、地址、金额、成本一律不下发 |
| 接口形态 | 新增 `GET /api/admin/mobile/pickup/orders`，删除旧列表 `/tasks` | 同一权限、同一服务、同一事实，不做两套列表；预览 `GET /tasks/{requestId}` 路径不变，确认仍走原 `POST /admin/orders/pickup/requests/{id}/fulfill`（锁、摘要、防重都不动） |
| 交付进度 | 列表返回整单 `pendingCount/fulfilledCount` | 交完一项后卡上仍显示「待交 0 项 / 已交 3 项」或移出待交页，但**不会**把「1/3 已交」显示成整单完成 |

## 改动清单

后端（只读，不新增表、不改库存与提货写入路径）：

- `core-domain/.../order/query/PickupTaskQuery.java`：`Task` → `OrderLine`（新增 `orderId/customerName`），`findTasks` → `findOrderLines(storeId, state, after)`，游标改为**订单 ID** 而非请求 ID。
- `core-infrastructure/.../order/query/PickupTaskQueryImpl.java`：派生表取 21 个订单，外层取这些订单**全部**请求行（含另一状态），`LEFT JOIN customer` 取姓名原文。
- `core-domain/.../repository/OrderPickupRequestRepository.java`、`core-infrastructure/.../OrderPickupRequestRepositoryImpl.java`：新增 `findByStoreIdAndOrderIds`（空集合短路，不生成 `IN ()`）。
- `core-application/.../PickupFulfillmentService.java`：抽出私有 `assemble(storeId, requests)`；新增 `listPickupRequestsForOrders`。
- `core-application/.../MobilePickupTaskService.java`：`listTasks/listOrders` 改为 `listOrders` + `Orders/OrderView/OrderLineView`；客户脱敏；`preview()` 未改。
- `api-admin/.../MobilePickupController.java`：基路径 `/api/admin/mobile/pickup`，`GET /orders`、`GET /tasks/{requestId}`，`no-store` 保留。

共享契约与员工端：

- `packages/mobile-contracts/src/pickup.ts`：新增 `PickupOrderLine/PickupOrder/PickupOrders` 与 `isPickupOrders`，删除 `PickupTasks/isPickupTasks`。解码器校验的**不变式**（不是简单字段比对）：
  - `pendingCount + fulfilledCount === lines.length`，且 `pendingCount === lines 中 PENDING 数量`；
  - 订单 ID 严格降序、不重复，跨订单请求 ID 不重复；`nextCursor` 只能等于最后一张卡的订单 ID，且只在 20 张卡时出现；
  - 待交页每张卡 `pendingCount ≥ 1`（整单已交完的单不许留在待交页），已提货页 `fulfilledCount ≥ 1`；
  - 历史项不得带 `unit/remainingQuantity`；可确认的待交项必须同时有单位和剩余量。
- `mini-staff/src/services/pickup.ts`：`readPickupTasks` → `readPickupOrders`（仍校验 `storeId` 与回显 `state`）。
- `mini-staff/src/pages/pickup/list/index.vue`：整单卡 = 订单号 + 待交项数 chip + `客户 X · 待交 N 项 · 已交 M 项` + 逐行物料（剩余数量/待核对/已交货 + 阻断原因）；点某一行仍进原请求详情页做逐批核对与交付；翻页按订单合并、同订单新卡替换旧卡。
- `mini-staff/src/styles/app.css`：新增 `.line` / `.line-done`（整单卡内的提货行）。

## 明确未做 / 未验证

1. **开发库无待交提货数据**（`status='PENDING'` 0 行、客户仅 2 行），未做真实数据下的分组、脱敏与余量渲染；也未插入测试数据（需用户授权才动开发库写入）。
2. **未做真机**：手册要求「同一单 20 行以上物料、多个货位/批次，用实际手机完成查看/扫码/未核对筛选/逐项交货」。本轮只做到「按整单看得见」，**逐项进度、只看未核对、本机准备勾选与恢复**仍在下一半。
3. **整单详情页未做**：当前进详情仍是按单条提货请求（扫码、勾选、交付）。手册要求的「整单逐条确认时显示还有几项待交」目前只在列表卡片上有整单口径，详情页内没有整单进度。
4. **配送备货清单未做**：手册「门店配送单的待备货与库房提货请求不是同一种对象，复用原 `order_delivery` 与 SALE 分配生成可读准备清单，不为方便出清单再建提货请求或再次扣库」——尚未开始，也未核查现有结构能否表达。
5. **手册接口表待同步**：`docs/superpowers/specs/2026-11-08-员工端小程序详细设计与实施手册.md` 第 118 行仍写 `GET /api/admin/mobile/pickup/tasks?state=&after=`。该文件当前有他人未提交改动（含 V2.1 补充设计），本轮未动，避免把他人 WIP 一并提交；下次该文件落盘时需同步为本轮路径。
6. 多人同时看同一任务仍无「认领/排他拣货」事实，本机勾选不代表他人可见的领取——手册已要求首期靠岗位约定，本轮未改。
