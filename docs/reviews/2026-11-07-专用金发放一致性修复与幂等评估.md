## 一、幂等：调查后暂缓（不是没做，是不该现在做）

### 取证事实

| 项 | 结论 |
|---|---|
| 前端调用方 | **无**。`admin-web` 全仓无 `grant-special-fund` 接口或发放 UI（Grep 全仓只命中 Controller、测试、2 个 Python 脚本与文档） |
| 实际调用方 | `scripts/test-e2e-flows.py:286`、`scripts/test-all-flows.py:344`，均**不带任何幂等键** |
| 既有幂等基建 | `V133__pos_sale_submission.sql`（`request_key` 主键 + 状态/哈希/订单号 CHECK）+ `PosSaleSubmissionService`；**POS 专用**，含 store_id/staff_id/order_id 语义，不可复用 |
| 真幂等的必要条件 | 新增幂等表或给 `wallet_transaction` 加 `request_key` + UNIQUE，并**强制客户端传 requestKey**（持久请求行锁 + 重放返回原结果），同时改两个脚本 |

### 判断

- 「重复点击重复发钱」在当前系统**没有可点的 UI**，是理论风险而非已发生的业务故障。
- 要做真幂等必须破坏性改 API 契约并新增 DDL，为不存在的调用方提前引入持久请求结构，
  与项目「不为未来可能需求提前引入复杂结构」「优先修复真实业务闭环」冲突。
- 用 Redis 短期去重不可接受：资金写入的幂等必须以持久事实为依据，
  与 POS 请求恢复契约「不能以 Redis 结果代替持久结果」一致。

**结论：本轮不做幂等**，不建表、不改接口。重开触发条件：出现真实的前端/小程序发放 UI、
或外部系统重试导致重复发放的实证、或合规要求发放必须可追溯重放。届时按 V133 的成熟模式
单独立项（持久请求表 + 唯一约束 + 内容哈希 + 重放 + 结果未知冻结），不与钱货主链混合实施。

## 二、本轮实际修复：余额与权益台账同事务

### 缺陷

`CustomerAdminController.grantSpecialFund` 原来先调 `walletService.addSpecialFund`
（该方法自带 `@Transactional`，返回即提交），**之后**在 Controller 里再调
`benefitLogRepository.save(benefitLog)`。两次写不在同一事务：台账保存失败时
余额已增加、权益台账缺失，且 Controller 承载了业务写入，违反分层约定。

### 改动（零 DDL、零 API 变更）

| 文件 | 改动 |
|---|---|
| `core-application/.../customer/service/SpecialFundGrantService.java` | **新增**：`@Transactional(rollbackFor=Exception.class)` 的 `grant(...)`，先调 `addSpecialFund` 再写 `CustomerBenefitLog`，两者同事务提交/回滚；金额防线仍留在 `WalletApplicationService.addSpecialFund` |
| `api-admin/.../controller/CustomerAdminController.java` | 注入新服务；发放入口改为一行 `specialFundGrantService.grant(...)`；删除 Controller 内台账构造与保存。`benefitLogRepository` 字段保留（发券入口 `:254` 仍用） |
| `WalletApplicationService` | **构造器与现有方法零改动**（这是选择新增服务而非给钱包服务加依赖的原因，现有 4 处显式构造测试不受影响） |

台账字段与修复前完全一致：`sourceType=3`、`benefitContent="专用金¥" + amount`、
`associatedId=null`、`createdBy` 取真实登录员工、`createdAt=now()`。

### 验证

- 定向 **10/10**：`SpecialFundGrantValidationTest 3`（金额防线）、
  `SpecialFundGrantServiceTest 3`（写入顺序/字段、钱包失败不写台账、台账失败异常传播）、
  `SpecialFundGrantHttpTest 3`（MVC 边界、身份覆盖、Controller 不再直接写钱包/台账）、
  `SpecialFundGrantTransactionTest 1`。
- **真实 Flex 事务回滚测试**：H2 + `FlexDataSource` + `FlexTransactionManager` + `TransactionTemplate`，
  两个仓储写入共用同一物理连接；台账写入抛异常后断言 `customer_wallet.balance` 回到发放前
  `10.00`、`wallet_transaction` 行数仍为 0 —— 直接证明「钱已到账、台账缺失」不再发生。
  模式沿用既有 `WalletAuthCodePrivacyTest`，未引入新测试框架。
- 完整后端：Java17 `mvn clean verify -B -Dmysql.it=true -Dauthority.mysql.it=true`
  BUILD SUCCESS，**145 报告 / 935 项 / 失败 0 错误 0 跳过 0**（较本日基线 931 项 +4，
  即新增 3 项服务单测 + 1 项真实事务回滚）；`scripts/verify-backend-reports.py` 门禁通过。
- 前端无改动，`npm test` 281/281。
