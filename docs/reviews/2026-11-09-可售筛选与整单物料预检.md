# 可售库存筛选与整单物料只读预检

日期2026-11-09；基线a20ee14；依据docs/current/13号决策。没有业务表迁移、原开发库部署或业务钱货数据修改；MySQL测试仅创建本次随机隔离库，CREATE成功才允许清理。

## 功能

1. 库存查询新增onlyHasSaleableStock，与原onlyHasStock分别表示可售和在手筛选，可同时使用。真实EXISTS/唯一有效基准/所有合法候选原批次单位核对写入COUNT/LIMIT之前，不在前端对一页过滤。合法候选保留日期参考但不排除日期已过，扣预留、仅启用货位。后台增加独立开关，重置时关闭新筛选；旧在手筛选语义保留。
2. 新POST `/api/admin/pos/catalog/stock-preview`，权限沿pos:order:create，服务端取真实员工本店、拒绝跨店。输入storeId/customerId及原单品/整套items（最多500行，展开物料最多1000行）；不接前端展开的套餐、不建订单、收款UUID/恢复记录或预留。
3. 套餐按PackagePricingService只读报价核原指纹后读取真实物料，单品/物料复用ProductUnitService换算及粒度校验，所有同商品需求按精确基准单位合并，再同findSaleableStock核对。多个套餐或不同单位与单品共用物料不会逐行虚假判够。
4. 返回裸DTO `{storeId:string,sufficient:boolean,issues:string[]}`；未知原单位不伪装0，量不足返回商品/整单需求/本店可售与单位。sufficient只表示此次快照，非预留、成交或价格承诺，最终原交易继续锁下复核。
5. PC进入结算弹窗前，员工端提交开单前调用。预检失败/未知停留当前清单，不写收款恢复；成功仍核当前会话、代次、客户、清单和交付选项，不允许把旧预检用于变更后的另一单。
6. PC显示正在核对状态，暂阻变更；离页使预检失效，旧成功不打开弹窗、旧失败不弹提示。员工busy和epoch/页面代次保护同理。真正提交后的未知仍由原POS恢复机制处理，未改变资金请求协议。
