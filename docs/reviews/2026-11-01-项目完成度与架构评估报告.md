## 一、总体结论

| 维度 | 评级 | 说明 |
|---|---|---|
| 门店进销存核心闭环 | **A-（可用）** | 采购→收货→批次库存→销售→收款→赊销→还款→退货→配送/提货→盘点/调拨 已闭环，且有多轮真实页面+SQL 对账证据 |
| 钱货事实正确性设计 | **A** | 单一库存账、追加写流水、请求幂等、退款不倒改事实，已有事务、锁、幂等及多轮事实对账证据；未进行同类系统质量排名 |
| 后台前端完成度 | **B+** | 静态页面盘点不代表逐页验收；上轮管理端275项通过，本轮修后结果另见验收记录 |
| 工程与分层纪律 | **C+** | 事务边界正确，但应用层直接依赖基础设施、裸 JDBC、God Service 明显 |
| C 端商城 | **D（几乎为零）** | 后端 8 个 Controller / 478 行，前端工程不存在，商品目录接口缺失 |
| 员工小程序 | **C（骨架 + 局部写入）** | 12页、E0–E4部分完成；小程序测试号开发工具已部分联调，未真机 |

**一句话**：这是一个「门店侧做得相当扎实、线上侧基本没开始、工程结构欠债累积到需要收口」的项目。最大的风险不是功能缺失，而是**在尚未收口的工程结构上继续叠加商城**，会把现在的「可控复杂度」放大成「不可控复杂度」。

## 三、架构评估

### 3.1 分层与依赖

```
core-domain (9,295 行)  ← Entity(@Table 67) + Repository 接口(66) + DomainService(14)
    ↑
core-infrastructure (8,681 行) ← Mapper(67) + RepositoryImpl(68)
    ↑
core-application (25,048 行) ← ApplicationService(52) + ★直接依赖 infrastructure
    ↑
api-admin (4,143 行) / api-client (828 行)
```

**做得对的**
- `@Transactional` 只出现在 `core-application`（43 个文件），Controller 与 domain 为 0 —— 事务边界位置正确
- Controller 不注入 Mapper/JdbcTemplate，48 个 Controller 无一个带事务 —— Controller 不承载业务规则，符合 AGENTS.md 第 5 条
- 端口-适配器在 domain/infrastructure 之间落地良好（66 接口 / 68 实现）
- 金额全 `DECIMAL` + `BigDecimal`，全仓零 `DOUBLE/FLOAT`；状态零 `ENUM`（用 `CHECK` 约束）—— 数据基础扎实

**真实问题**
1. **`core-application → core-infrastructure` 依赖倒置**（`core-application/pom.xml:19-30`）。pom 注释自述理由仅为「复用错误码/异常」—— 这些应抽到独立 `common` 模块。后果：架构约束在编译期失效。
2. **应用层直接 import Mapper**：17 处，最严重 `ReportAnalysisService.java:12-19` 一次性 import 8 个 Mapper。
3. **应用层裸 `JdbcTemplate` 手写 SQL**：8 个文件 32+ 段（`InventoryLedgerService` 13 段、`MobileScanQueryService` 10 段等）。
4. **库存同表双实现**：`inventory_batch_balance` / `inventory_movement` / `inventory_location` 等既有 MyBatis Mapper（`…ForUpdate`），又有 JDBC 手写 `FOR UPDATE`（`InventoryLedgerService.java:227,232,295…`）。两套加锁路径 = 一致性隐患最大项。
5. **God Service**：`OrderApplicationService.java` 2,279 行，单方法 `createPOSOrder` 约 430 行，混装下单/支付/退款/回调/查询。
6. **死资源**：`spring-boot-starter-data-redis`（`core-infrastructure/pom.xml:55-59`）与 `deploy/docker-compose.prod.yml:24-30` 的 redis 容器，Java 代码零引用。

### 3.2 同一进销存服务支撑两端

当前复用同一商品、单位、价格、库存和客户资产事实，符合小门店MVP与禁止第二可写数据来源的约束。客户端应通过真实身份和最小DTO使用这些事实，而不是另造一套商品/库存。

员工端接口命名为/api/admin/mobile及原业务入口，不代表拥有后台全权限。真实员工身份、门店隔离、逐接口权限、最小返回字段与实际网关暴露才是安全边界；本轮已验证最小配送岗位不能查询全店订单。确需独立部署隔离时可评审/api/staff，不默认引入双写入口。

api-admin与api-client可按现有边界继续；客户目录/页面仍缺实现。真实支付及公网发布前须补相应鉴权、流量限制、外部资金补偿和对账验收，但不据接口前缀推断当前系统“失控”。

### 3.3 商品模型是否需要重构

不另建商品档案，也不因商城可能存在就默认增加渠道发布表。当前每个具体品规可维护为一个商品，袋/瓶/箱是直接单位换算，不是必须新增SKU层的证据。

product_unit是换算唯一来源；product.main_unit仍承担商品主单位展示及维护职责，aux_unit/main_to_aux_ratio等历史兼容字段须逐调用审查，不应笼统当只读投影全部删除。

门店启用状态status与商城展示is_online应在界面明确含义。单图、文字详情和基础运费可先复用现有字段，通过客户只读DTO限制敏感信息；没有真实多渠道差异、发布审核等需求前，不新增product_channel_listing或第二套上下架来源。只有实际经营需求超出当前结构时，再评审发布视图。

### 3.4 价格体系是否过于复杂

**结论：定价本身已经收口得很干净；复杂的是「促销资产载体」，而这部分确实过重。**

参与真实报价的只有两项：
1. 商品：`基准单位单价（零售价 or 会员价）× 销售单位系数`，会员是二值判定（`ProductPricingService.java:40,73-75`）
2. 套餐：`元/套` 独立价 + 按分分摊到物料（`PackagePricingService`）

`storeId / channel / vipLevel / businessDate` 在 `PriceContext` 里**只进不出、原样回填**，不参与计算（`ProductPricingService.java:51-53,63`）。多维定价能力已被 `V130` 主动删除 —— 这是**正确且克制**的收口。

冗余与噪声（应清理）：
- `product_price` 表：写入被三处 `throw` 硬禁（`ProductApplicationService.java:635/641/649`），仅剩只读历史查询；V126是已经发生的历史迁移，并非仍在扩展。保持归档，不修改历史迁移
- `online_price` 列：同批代码与V136已删除独立线上价，线上继续走统一报价；数据库升级后旧包不兼容，见迁移运行说明
- `main_unit/aux_unit/main_to_aux_ratio` 与 `product_unit` 双轨

真正过重的是客户侧「可抵扣资产」，共 6 种：
优惠券 / 专用金 / 本金余额 / 积分 / 充值赠送规则 / VIP 月权益

对一家小规模农资门店，建议收敛为两类语义：
- **一次性凭证**：优惠券（整单、一次性核销、不找零）、积分兑换
- **账户余额**：本金（客户自有资金）、赠送金（商家赠送资金）

### 3.5 已有优惠券的前提下，「专用金」是否必要

先把专用金拆成两个独立属性再判断：

**属性 A：赠送资金与本金分账** —— **必要，不能省**
- 依据：`customer_wallet` 按 `wallet_type`（1本金/2专用金/3积分）分行（`V8__wallet.sql:6-18`），成本极低
- 不可替代性：退款必须原路返回（`refundSpecialFund`）、财务要区分「客户自有资金」与「商家让利」、客户争议与税务口径都需要这条边界。**券是凭证不是余额，无法承担「余额沉淀 + 原路回退」**

**属性 B：按商品行限制 + 可部分抵扣**（`product.allow_special_fund` → 快照到 `order_item` → `OrderDomainService.calculateMaxSpecialFundAmount` 逐行累加 → 支付瀑布第 2 级）—— **可选，是复杂度主要来源**
- 券已有的能力：`min_order_amount` 门槛、`limit_category_id` / `limit_product_id` 限品类限商品、有效期
- 券做不到、专用金能做到的：① 同一单里「只允许 A 行抵扣、C 行必须现金」；② 部分抵扣不找零（余额 200、本次可用 5 → 只扣 5）；③ 套餐内按物料分摊额计算额度
- 关键判断：**如果门店没有「同一单内按商品区分能否用赠送金」的真实诉求，属性 B 就是纯成本** —— 它带来商品开关、订单行快照、套餐分摊上限、支付瀑布等一整套链路

**风险（若保留）**
- 专用金**无有效期、无门槛**，是长期挂账负债，需对账报表
- 手动发放入口 `CustomerAdminController.java:266-306` 无审批、无额度上限 → 内控风险
- 4 个来源（充值赠送 / VIP 月权益 / 手动发放 / 退款回退）分散在 4 处，缺少统一的「赠送金台账」

**建议**
- **保留属性 A**（赠送余额账户），这是必需的财务边界
- **属性 B 先向业务确认**：若老板确实要「化肥不能用赠送金、农药可以」，保留并补齐：有效期、发放审批与额度、赠送金台账报表；若无此诉求，降级为通用赠送余额，用券的限品类表达商品限制，可删除商品开关、订单行快照、套餐分摊上限三处逻辑

## 五、改进建议与优先级

### 先修真实不一致与运行边界

1. 新建采购行额与总额统一到分；保留实际单位进价和收货成本，验证前端、真实HTTP及落库。
2. 纠正开发库已到V138的事实，保留迁移校验值；补旧绩效非空保护、停写与数据库级回退说明，不补造已删历史。
3. 保留统一报价、原资金库存事实、最小岗位权限和请求恢复约束；继续员工端弱网/杀进程、安卓/iPhone真机等未验范围。
4. 验证托管平台实际CI执行；GitHub配置包含master、前端测试与类型/构建，但当前Gitee仓库没有远程流水线成功证据。

### 客户端按已批准业务逐步实现

5. 先复用客户身份、商品档案及统一价格，补实际需要的只读DTO与小程序页面，避免成本/利润/货位等字段外泄。
6. 农技咨询、老板经验沉淀和员工培训继续按已批准双端计划推进；渠道发布新表、预占库存和专用金规则变更不默认同时实施。
7. 真实支付须具备网关、验签、交易防重、资金库存失败补偿及对账验收；测试号不代表支付资质，当前主动确认继续默认关闭。

### 仅在证据或规模要求出现时评审

8. 库存访问职责收敛、common拆分和订单服务拆分属于可维护性工作，先识别具体重复/故障和事务边界，不作为P0全量改造。
9. 独立员工前缀、多实例共享会话、监控与依赖升级各自有适用前提，不凭接口命名、字段比例或未经核实的最新版本制造必须重构的结论。
10. 不引入额外SKU/渠道体系、微服务、消息队列或第二套可写库存价格；已有事实和契约是逐步改进的基础。
