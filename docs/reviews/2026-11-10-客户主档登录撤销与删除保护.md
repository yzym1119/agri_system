# 客户主档登录撤销与原删除保护

日期：2026-11-10。源基线8559e49；本批为该基线后的客户主档版本改动，具体提交以Git记录为准。**自动验证通过，独立审查因服务额度限制尚无结果，不合master、不作为正式发布结论。**

## 为什么改

员工端与未来客户端共用客户主档。V144只能撤销一条微信身份；主档停用再恢复、身份行未变时，旧客户token可重新访问原资源。需要主档自己的持久版本，不能用普通业务version或清Redis替代。本批不新建表、不提供尚无审计的停用/恢复按钮。

V146只给customer增加auth_version BIGINT NOT NULL DEFAULT 1，保留客户状态、联系方式、订单和三钱包事实。客户端token保存原customerAuthVersion，每次本人资源重核主档与原身份版本。缺旧字段必须重新登录；恢复启用不恢复旧会话，新平台登录才能取得新版本。普通登录、姓名等资料更新不递增，不互踢正常设备。

## 实现范围

- CustomerRepositoryImpl：同Flex连接手动读取安全白名单，不继承外层DTO映射；保存核原行锁、原正数版本及条件更新。状态变化递增，陈旧/缺失/溢出拒绝。逻辑删除独立入口递增一次，不允许普通保存恢复已删档案。
- AuthService：真实微信绑定与显式非prod DEV均保存主档版本。本人ID及资料二次读取核原版本；身份行检查保留，没有在身份锁后追加客户行锁。
- 原删除路径：先持原客户锁，再按实际READ_COMMITTED读余额/未结欠款/进行中业务。remaining_amount>0即欠款，不能因逾期3或未知状态漏检。不新增资金写入、不改钱包及原交易归属。
- 驱动useAffectedRows=true返回0时，仅普通无变化保存可经当前状态核对接受；未知deleted不伪装成功。保持原事务适配与连接，不替换数据源。

## 失败复现与修复

1. 实际随机MySQL + 原AuthService登录，仓储停用再恢复，旧token原行为未抛错；新增客户主档版本后旧token拒绝，新token成功。
2. 无变化保存遇useAffectedRows=true被误判陈旧，实际驱动复现后补精确无变化处理。
3. 原欠款二次按status=1过滤，逾期未结款删除用例先失败；移除状态误过滤后通过。
4. 实际MySQL客户行锁与performance_schema.data_locks证明删除正在等待另一线程入账；原流程先查旧余额，待锁后仍删除成功。改先持客户锁后看到已提交123.45余额并拒删。
5. deleted=NULL夹具被MyBatis逻辑过滤更新0行，旧无变化兜底却返回成功；先失败后改为明确deleted=0才允许保存。
6. 首次完整验证在两份手建报告夹具缺AUTH_VERSION处出错，补真实V146字段，未放宽产品查询。既有停用提示保持原HTTP契约。最后补强“身份行版本缺失”测试：主档版本有效，只缺身份版本，确保不是被新增主档检查提前拒绝而虚假覆盖。

前述平台返回是受控替身，不是微信平台真实授权；MySQL连接、仓储、事务和锁竞争为实际执行。
