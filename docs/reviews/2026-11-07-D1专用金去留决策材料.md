# D1 专用金「按商品行限制」去留 · 决策材料

日期：2026-11-07
性质：**只读调查 + 决策对照，未改任何生产代码、DDL、数据**。
来源：清单 D1（`docs/reviews/2026-11-01-修复优化清单.md:229-237`，P1 / 待业务确认）与
评估报告 `docs/reviews/2026-11-01-项目完成度与架构评估报告.md:153-175`。

> 一句话结论：**「赠送金与本金分账」必要且不能省；「按商品行限制」是可选复杂度。**
> 去掉它只需改 4 个文件约 40 行、零迁移零数据风险，但会永久失去「同一单内按商品控制让利资金流向」的能力。
> 无论选哪个方案，都有一项与决策正交的真实缺陷应先修（发放金额无校验/无额度）。

## 一、先纠正评估报告里的两处旧说法

| 旧结论 | 代码事实 | 影响 |
|---|---|---|
| 「4 个来源无统一台账」 | **有 3 张台账**：`wallet_transaction`（V8:21-41，含前后余额快照）、`customer_benefit_log`（V68:5-17）、`vip_monthly_record`（V41:30-41，防重发） | 台账不是缺口，缺的是**审批、单次/累计额度、有效期** |
| 「按商品行限制 + 套餐分摊上限」是一套完整能力 | `product_package.allow_special_fund`（V38:23）**Java 零引用、前端无配置入口**，是僵尸列；套餐实际通过**物料商品的开关**间接计算（`PackagePricingService.java:98-112`） | 套餐维度没有独立控制，现有「按行限制」只到商品物料粒度 |

另核实：`GrantSpecialFundCommand.java:13-26` 无任何约束注解，`CustomerAdminController.java:269` 的 `@Valid` 因之空转；`WalletApplicationService.addSpecialFund:320-342` 无上限校验，正数仅由领域实体 `CustomerWallet.add:78-80` 兜底（异常变成 HTTP 500 而非 400）。对照 `grantBalance`（`CustomerAdminController.java:316`）至少有正负分流。**这是无需业务决策即可修的防御性缺陷。**

## 二、券与专用金的真实差异（不是重复造轮子）

| 维度 | 优惠券 | 专用金（wallet_type=2） |
|---|---|---|
| 本质 | 一次性核销**凭证**：`customer_coupon.status/used_order_id`，无余额字段 | **账户余额**：`customer_wallet.balance` 按 wallet_type 与本金分两行 |
| 找零 | **不找零**，面额大于订单额时差额作废（`V69:5-8`、`CustomerCoupon.java:166-171`） | 部分抵扣 `min(remaining, 上限, 余额)`，余额留账（`OrderPaymentService.java:100-106`） |
| 商品限制 | 限商品/限品类是**整单「包含即准入」**，不按行分摊（`CustomerCoupon.java:97-109`） | **逐行**累加允许行 `totalPrice`（`OrderDomainService.java:53-62`） |
| 有效期/门槛 | 有（`CustomerCoupon.java:83-95`） | **无**（`customer_wallet` 无 expire_at / min_amount）→ 长期挂账负债 |
| 退款 | 不转余额；仅「净成交全冲销 + 全部物料实退」才恢复凭证状态，过期不恢复（`OrderPaymentService.java:457-481`） | 按支付流水**原路退回** `wallet_type=2`（`:360-361` → `refundSpecialFund`） |
| 资金口径 | 成交优惠，冲减 `order.payAmount`，不生成实收流水 | 生成 `order_payment` 实收流水（payment_method=8），计入退款资金来源 |
| 分账意义 | — | 与本金 `wallet_type=1` 分账：退款 `refundBalance` / `refundSpecialFund` 两条路径，财务可区分自有资金与让利 |

**因此「有券了还要不要专用金」要分两层答**：
1. **分账层（必要）**：券承担不了「余额沉淀 + 部分抵扣 + 原路回退 + 财务分账」。删掉 `wallet_type=2` 会破坏退款资金守恒与 AGENTS.md 账款契约，**不建议动**。
2. **限制层（可选）**：`allow_special_fund` 带来的按行上限、套餐分摊、商品开关、前端额度预演，才是复杂度主体。

唯一真正只有按行限制能表达的场景：**同一笔订单里，指定某些商品必须用现金/本金付款、只有允许行可用赠送金**（例如厂家返利/补贴专款只能买指定品类）。券做不到（整单准入），通用赠送余额也做不到。

## 三、两个方案对照

### 方案 A · 保留按商品行限制
- **适用**：确实存在「赠送金只能买指定商品/品类」的经营或合规规则；或已在给客户宣传该规则。
- **保留代价**：继续维护 **66 处 / 34 文件**的 `allow_special_fund` 引用（其中代码+测试 62 处 / 31 文件）与 31 处额度计算引用；`CheckoutDialog.vue` 自行预算额度、后端再算一次，两处口径需长期同步。
- **必须补齐的治理**（否则是负债风险，非功能问题）：
  1. 发放入口加 `@NotNull / @DecimalMin("0.01") / @Digits` 与单次上限（当前完全无上限）
  2. 明确专用金是否设有效期 —— 若要，需新增字段 + 到期处理 + 负债核销规则，属**独立子项**（会新增字段，需单独授权）
  3. 决定 `product_package.allow_special_fund` 是补配置入口还是标注废弃（当前僵尸列）
- **风险**：无门槛、无有效期的余额是长期挂账负债；发放无额度可无限增发。

### 方案 B · 降级为通用赠送余额（保留分账，去掉按行限制）
- **适用**：没有「同单按商品区分让利资金」的真实诉求；商品限制交给券（限商品/限品类）。
- **最小改动路径（推荐先评估这个，而不是大拆）**：
  1. `OrderDomainService.calculateMaxSpecialFundAmount:53-62` 去掉 `.filter(allowSpecialFund==1)`，改为全量 `totalPrice` 求和 —— **一处即覆盖全部 3 个后端调用点**（`:100`、`PosOrderCreationService:363,422` 均传全量明细）
  2. `PackagePricingService.java:98-112` 的 `specialAmount` 改取套餐总额
  3. `CheckoutDialog.vue:513-534`：`hasSpecialFundProducts` 恒真、额度取整单额，**下线 `:160` 的「仅覆盖允许专用金的商品金额」提示**
  4. `pos/index.vue:530` 套餐额度取 `quote.totalAmount`
  → **4 个文件约 40 行**；DDL / DTO / Mapper / 商品档案 / Controller 全不动，**零迁移、零数据风险**。
- **DDL 处置**：三个 `allow_special_fund` 列**都不删**。`order_item` 是历史订单快照（`V36:57-58` 注释「来源于商品快照」），删列破坏历史对账；另两列保留成本≈0。只需停止写入或恒写 0，不必加迁移。
- **测试代价**：预计 **8~12 个用例 / 6 个文件**断言需改（`OrderPaymentPreviewTest`、`OrderApplicationServicePaymentFlowTest`、`PackagePricingServiceTest`、`ClientCouponSettlementTest`、`pos-pricing-regression.test.cjs`、`RetailFactChainEndToEndTest`）。
- **不可省略的同步点**：前端额度预演与后端计算**必须同批改**，否则会出现「页面显示不能抵扣、后端实际抵扣」。
- **永久代价**：失去按商品行控制让利资金流向的能力；日后若出现补贴/专款专用诉求，需要重新引入这套链路。

### 方案 A-（折中）
保留按行限制，但本轮只做「与决策正交的三件事」：补发放校验与额度、明确套餐僵尸列处置、把前端额度预演改为直接消费后端报价指纹（消除双算口径）。不碰业务规则，等真实诉求明确再决定 A/B。

## 四、数据现状（决策前必须看生产库）

本机开发库 `agri_system` 是**空业务库**：`customer_wallet` 总 0 行、`order_payment` 总 0 行、`product` 总 0 行，
故 `wallet_type=2` 余额、`payment_type=8` 流水、`allow_special_fund=1` 商品三项 COUNT 均为 0。
**这不能证明生产无数据**。若选 B，上线前需在生产库统计：

```sql
SELECT COUNT(*), SUM(balance) FROM customer_wallet WHERE wallet_type=2 AND balance>0;
SELECT COUNT(*), SUM(amount) FROM order_payment WHERE payment_type=8;
SELECT COUNT(*) FROM product WHERE allow_special_fund=1;
```

有余额或有历史流水时，方案 B 仍安全（分账与回退链路不变、快照列保留），但需补一轮「历史订单以旧规则展示、新订单以新规则计算」的对账说明。

## 五、需要你拍板的三件事

1. **是否存在「赠送金只能买指定商品/品类」的真实经营或合规要求？**
   - 有 → 方案 A（并补治理）
   - 没有 → 方案 B（最小改动 4 文件）

2. **若选 A**：`product_package.allow_special_fund` 是补套餐配置入口，还是明确标注废弃（当前零引用）？
3. **专用金是否要有有效期？** 要的话会新增字段与到期/核销规则，是独立子项，需单独授权；不与 A/B 一起做。
