## 本批范围

1. 原CustomerApplicationService建档及三个零余额钱包创建体提取到CustomerRegistrationService，后台与新客复用。程序比对原创建体逐字一致，保留原普通客户/版本/时间/编码及后台详情返回，不发会员/绩效/收款/库存事件。
2. 新V145一张customer_identity_enrollment记录固定申请、当前微信锚与一次核验决定。通用日志无唯一请求/待办/固定结果，身份表又需要已有客户，因此不能直接复用；不复制客户或钱货，不预建通用工作流。
3. PHONE_VERIFIED提交原UUID与可选姓名；AppID/OpenID/号码只从实际证据读取。任一手机号命中（当前实现为精确号码匹配，含停用/删除）只REVIEW_REQUIRED，不建空客户或副档案。无匹配才同事务创建客户、三零钱包、当前AppID身份与申请结果。
4. 返回CREATED并不发CUST会话，需新真实微信登录。申请结果可由同微信短时凭据或真实WECHAT客户会话读取，DEV/STAFF拒绝；查询UNKNOWN不证明未落库，固定原UUID核对。
5. 后台初次LINK/REJECT要求实际当前员工、新身份权限与原customer:query同时具备。只关联启用未删除且无同App身份冲突的目标；停用旧关联不直接覆盖。记录独立决定UUID/摘要/员工/方式/原因及身份版本快照，原手机号、钱包和历史单据不改。拒绝后可重申，旧结果不覆盖。

## 结构与接口

| 入口 | 数据/权限边界 |
|---|---|
| POST `/auth/client/onboarding/registration` | `{requestKey,displayName?}`，必须真实PHONE_VERIFIED，不信自报客户/手机号 |
| GET `/auth/client/onboarding/registration/{requestKey}` | 同AppID/OpenID，本人原请求，返回requestKey/status/nextAction，无客户/财务或登录token |
| GET `/api/admin/customer-identities/enrollments` | status/before，20条游标；identity:query与customer:query |
| GET `/api/admin/customer-identities/enrollments/{id}` | 申请/脱敏微信/手机号、候选基本资料及决定；不拼钱包/欠款 |
| POST `/api/admin/customer-identities/enrollments/{id}/decision` | identity:bind与customer:query；独立UUID、LINK/REJECT、目标、核验方式/原因；同请求仅原员工原内容可重放 |

V145真实菜单项为customer:identity:query、customer:identity:bind，不自动授权任何角色。客户档案是原全局档案，无store_id，不在此凭空增加门店归属或放宽原财务可见权限。

申请表保存request_key/fingerprint/app_id/open_id/phone/display_name/verified_at，active_subject，状态/原因，完成客户及身份ID/版本，以及一次决定的独立key/摘要/员工/方式/原因/时间。三唯一键分别保护请求、当前锚及决定；拒绝释放锚为NULL，原行保留。

## 发现与修正

- 初次真实MySQL的客户ID回填异常来自新测试夹具：Mapper在Flex全局配置前注册，1.9.6会得到NoKeyGenerator。对照实际依赖源码并单独复现后，夹具改为先建工厂/全局配置再注册Mapper；未修改产品主键策略或补造ID。
- 十并发暴露upsert与OR二级索引FOR UPDATE反向锁序。只加1213有限重试仍在完整回归失败；实际本机InnoDB诊断确认主键→唯一索引与唯一索引→主键相互等待。改非锁定定位、只按主键加锁后，三轮各十请求通过。
- 原UUID拒绝后重申，新锚使原请求OR查询选两行，POST重放无法返回原REJECTED。独审指出、真实MySQL先RED，改原UUID优先；进一步构造“原初查空→并发完成/拒绝R1并重申R2→原请求恢复”仍RED，最终在upsert之后也再次优先原UUID，只缺原key时查当前锚。最新补丁H2两项及静态补审通过，真实MySQL复测待执行。
- CUST认证后第二次读取身份若OpenID/版本改变，旧token可能派生新主体。真实MVC顺序v1/v2先RED，第二次读取补原token authVersion比较后，全量检查点通过。
- 注册入口用当前Flex管理器TransactionTemplate实际READ_COMMITTED，拒Spring和原生Flex外层事务。只在SQLState40001/error1213明确整笔回滚后有限重试原不可变输入；08S01等提交未知不自动重试。原生XID仅Spring标记未识别的问题先RED后补保护。
- 审查最初提出Flex吞提交异常，简化探针直接hold原连接不含生产代理，不能作实际结论。真实FlexDataSource→当前JdbcAccessConfig→TransactionTemplate→物理提交故障链会传播08S01；提交前/实际提交后丢响应均不返回成功，XID清理且下一事务可用。审查已撤回原判断，未改公共数据源/事务适配。
