# 移动开单：选客户/选商品重做与结算、履约方式核对

日期：2026-11-08
范围：`packages/mobile-contracts`、`mini-staff`、`api-admin/PosCatalogController`、`core-application/PosCatalogApplicationService`、`PosOrderCreationService`、`PosOrderInputPolicy`、`core-domain/CustomerRepository`、`core-infrastructure/CustomerRepositoryImpl`
DDL：无新增迁移、无表结构变更、无数据变更

## 一、结论摘要

1. **移动开单仍按既定设计实现**：写入口只有一个 `POST /api/admin/orders/pos`，命令里**不含任何成交金额**，价格指纹来自后端报价；持久请求协调器 `createPOSRecovery`（`submitOnce`/`restore`/`finishCompleted`/`cancelPending`）未被绕过。这一点没有偏离。
2. **但第二阶段设计里的两处与本次要求冲突，已改**：赊销（支付方式 6）从员工端移除；门店配送不再手填收货人/电话/地址，改为选后台客户档案后由后端带出。
3. **商品、价格、库存本来就走后端，且与后台同源**（详见第三节链路）；真正没打通的是**客户**：原页面只能手输客户 ID，而客户列表接口要求 `customer:query`（V59 只给 `pos:order:create` 配了 SUPER_ADMIN），店员实际拿不到客户。本轮新增只读接口 `/api/admin/pos/catalog/customers` 补齐。
4. **发现并修复 4 个真实缺陷**：报价未传 `storeId`、库存完全没接、成交后未清理本机原请求（第二单被"上次收银未核对"拦住）、配送收货信息与档案可能不一致。
5. 后端全量测试 6 模块 BUILD SUCCESS，契约 58/58、员工端 94/94、类型检查干净、`build:mp-weixin` 通过；真实 HTTP 下单 3 单、模拟器实机走通全流程。

## 二、现状核对：是否仍按第一阶段设计

| 设计约束（第一阶段确定） | 当前实现 | 判定 |
| --- | --- | --- |
| 成交金额只能由后端算，前端不报价 | `buildSaleCommand` 只发 `productId/quantity/unit/quotedUnitPrice` 指纹，无 `unitPrice`/`payments`/`discountAmount` | 保持 |
| 唯一写入口 + 请求号幂等 | `submitSale` 走 `posRecovery.submitOnce`，`requestKey` 由协调器生成，结果未知返回 `VERIFYING`，不换号重收 | 保持 |
| 待核对/已完成必须在订单/提交表留痕 | `/pos/submissions/{key}`、`/cancel` 未改 | 保持 |
| 员工身份与门店由后端解析 | 门店取自 `staff.storeId`，前端传的 `storeId` 不参与扣减 | 保持 |
| 第二阶段加的赊销 | 页面与契约层均已移除（后端能力保留给后台收银台） | **已按本轮要求改造** |
| 第二阶段加的手填收货信息 | 改为选客户档案带出，三项收货信息恒为 `null` 上传 | **已按本轮要求改造** |

覆盖度：目录/报价/创建/提交查询/取消五个接口全部有前端调用方且都有测试；**未覆盖**的是后台收银台独有的优惠券、整单优惠、人工改价原因、余额与混合支付、专用金——这些仍在后台，员工端不提供。

## 三、数据来源链（是否后端、是否与后台相通）

### 3.1 商品

```
mini-staff/services/sale.ts  searchProducts()
  → GET /api/admin/pos/catalog/products?keyword=&pageNum=1&pageSize=20
  → PosCatalogController.products()
  → PosCatalogApplicationService.products()
  → ProductApplicationService.queryProducts(keyword, status=1)
  → product 表（与后台「商品管理」同一张表、同一仓储）
```

只读投影已过滤成本、备注等内部字段；`keyword` 走 `ProductRepositoryImpl.findActiveByKeyword`（`code`/`name`/`COALESCE(barcode)`）。
**结论：商品确实从后端取，与后台同一数据源，改动后台商品立即可见。**

### 3.2 价格

```
GET /api/admin/pos/catalog/products（无价格字段）
  → 每行按需 GET /api/admin/products/{id}/price-quote?storeId=&customerId=&quantity=&unit=
  → ProductPricingService.quote()：按持久化基准单位系数换算，有效会员取 vipPrice，ruleVersion=MEMBER/RETAIL
```

页面上的 `¥xx/基准单位`、小计都来自报价，前端不算成交价，只用 `suggestedUnitPrice` 当指纹。
**本轮修复**：原来 `quoteProduct` 没传 `storeId`，而报价接口契约本就按门店解析；虽然当前实现未使用该参数，仍属契约漏传，已补 `staffAuth.current()?.storeId`。

### 3.3 库存

```
GET /api/admin/pos/catalog/inventory?pageNum=1&pageSize=500
  → inventory 快照表（本店可用量）
```

**本轮新增**。此前页面完全不显示库存，选商品等于盲选。现在商品行显示「编码 · 库存 N」并注明**只作参考，出库时以后端可用量为准**。

门店隔离已由后端保证：`PosCatalogApplicationService.inventory` 的 `scopedStore()` 在请求不带 `storeId` 时取 `CurrentUser.storeId()`，非管理员传别店直接抛「不能读取其他门店库存」；下单扣减用订单门店（`staff.storeId` → `order.store_id`）。

口径差异（本轮复核发现，未修）：这里读的是 `inventory.quantity` 投影，而真正扣减读 `inventory_batch_balance` 的 `base_quantity - reserved_base_quantity`，并排除过期批次与停用货位。开发库当前无预留/过期/停用货位，两者实测一致（93/60/40），但这是结构性的：一旦出现预留或过期批次，展示值就会大于可售量。整改方案见 `2026-11-08-库存口径与员工端范围确认及下一步排期.md`。

### 3.4 客户（此前未打通）

```
GET /api/admin/pos/catalog/customers?keyword=&limit=20   ← 本轮新增
  → PosCatalogApplicationService.customers()
  → CustomerRepository.findActiveByKeyword(keyword, limit)   ← 本轮新增
  → customer 表（status=1、deleted=0，name/code/phone 模糊匹配，created_at DESC）
```

返回 `PosCustomerVO`：`id/code/name/phone/address/type/vipLevel/vipActive`，**刻意不含余额、专用金、欠款、积分、归属员工**——避免把资金档案读权限随收款权限一起放开。`vipActive` 用 `isVip() && !isVipExpired()`，与 `ProductPricingService.buildCustomerContext` 同口径，会员 chip 不会把过期会员显示成会员。

为什么必须新开接口：`GET /api/admin/customer/list` 要求 `customer:query`，V59 只给 SUPER_ADMIN 分配了 `pos:order:create`；店员若被授予收银权限却打不开客户列表，只能手抄客户 ID——这不只是体验问题，手抄 ID 极易串号，把单开给别人。

## 四、本轮改造

### 4.1 选客户

- 顶部客户卡：未选时显示「散客（不记客户）」，已选显示姓名 + 会员 chip + 「切换」。
- 点击弹出底部面板：搜索框（姓名/编码/手机号）→ 防抖检索 → 结果行显示姓名、编码、手机号、地址摘要；底部固定「不选客户，按散客开单」。
- 会员 chip 只表达身份与价格档，**不显示余额**（员工端没有资金档案权限）。
- 客户变更后，购物车全部明细按新客户重取报价指纹（会员价可能变），慢的旧请求结果按序号丢弃，避免把旧客户的价安到新客户头上。

### 4.2 选商品

- 搜索 → 结果行显示「编码 · 库存 N」+「¥xx/基准单位」。
- 点行弹出数量面板（`-` / 输入 / `+`，步进 1，支持 0.5），确认后入购物车；数量、单位、报价指纹一起固化。
- 购物车行不再允许直接改价（员工端无人工改价权限），只能删行重加。

### 4.3 结算方式：只剩现金

页面固定一张只读卡「现金 · 线下实收」，**没有可选按钮**，契约层同步收窄：

```ts
export type SaleOptions = { paymentType: 1; customerId: string | null; deliveryType: 1 | 2; remark: string | null };
// resolveSaleOptions：paymentType !== 1 → throw PAYMENT_INVALID
```

**为什么只有现金一种**（按能力逐项说明，不是偷懒）：

| 方式 | 员工端不可用的真实原因 |
| --- | --- |
| 微信/支付宝（2/3） | 无商户号与真实支付通道，未接支付回调；后台也只能走"线下已收"登记 |
| 余额（4） | 需要钱包授权码（`walletAuthCode`）与客户资金档案读取，员工端无授权码录入流程，也无资金权限 |
| 赊销（6） | 需要信用额度、禁售名单、审批链，且**用户本轮明确要求移除** |
| 混合（10） | 需要多笔支付明细交互，前提是上面几种先可用 |
| 专用金 | 需按商品行开关 + 钱包授权码，同余额 |

后端 `validatePosPayments` **未改**（仍接受 1/2/3/4/6/10），这是有意的：后台收银台仍在用这些方式，收窄只发生在员工端与其契约层。这是"能力不对称"，不是缺陷，但要知道：**员工端能开的单只是后台能力的子集**。

### 4.4 交货方式：门配改选客户

- 「当场交货」/「门店配送」两个按钮；选配送且未选客户 → 红色阻断「门店配送需要先选客户，收货人、电话与地址由客户档案带出」。
- 选中客户后展示三行**只读**收货信息（收货人/电话/地址），来自档案，不可编辑。
- 档案缺手机号或缺地址 → 阻断并提示"请先在后台补全，或改为当场交货"，不允许带着残缺地址出门。
- 上传命令里 `receiverName/receiverPhone/receiverAddress` **恒为 null**，由后端按 `customerId` 带出。

后端策略 `PosOrderInputPolicy` 重写为两段：

```java
// ① 不查库的结构校验，放在开单最前（非法输入不进读取流程）
static int validatePosDelivery(POSOrderCreateCommand command)   // 1/2；只填一部分 → 拒绝
// ② 客户行锁之后，三项全空才按档案带出
static void fillPosDeliveryFromCustomer(POSOrderCreateCommand command, Customer customer)
```

- 两条合法来源，**不允许"两边各填一半"**：拼出来的收货信息无法追溯来源，配送员按错误地址跑一趟的代价高于拒绝开单。
- 客户档案 `status=2`（停用）→ 拒绝开配送单。
- 档案缺项 → 拒绝，且在**任何写事实之前**（订单、订单行、收款流水、库存出库、事件均未发生，有 `verifyNoBusinessWrites()` 断言）。
- 后台收银台历史行为完全保留：三项填齐照样能开配送单，以手填为准。

## 五、发现的不一致与整改

### 已修（本轮）

| # | 问题 | 后果 | 处理 |
| --- | --- | --- | --- |
| 1 | `quoteProduct` 未传 `storeId` | 报价契约按门店解析，前端漏传，一旦后端启用门店价就会串价 | 补参数 |
| 2 | 库存完全未接 | 选商品等于盲选，必到出库才报"库存不足" | 新增 `readStock` 只读展示 + 明确"以后端为准" |
| 3 | 客户只能手输 ID，且店员无 `customer:query` | 手抄串号 → 单开错人、会员价算错 | 新增 `pos:order:create` 权限下的只读客户检索 |
| 4 | 成交后未清理本机原请求 | **第二单必定被"上次收银结果尚未核对"拦住**（模拟器实测复现） | 成功后 `posRecovery.finishCompleted(orderId, true, readPOSResult)`；核对失败则保留，仍按待核对处理 |
| 5 | 配送收货信息靠手抄 | 与档案不一致，配送员按错地址跑 | 改为选客户档案带出；后端禁止填一半 |
| 6 | 单测 fixture 与新策略顺序不符 | 配送缺电话的用例在员工查找处先失败，断言失真 | 结构调整校验提前 + 补 3 项分支测试（档案带出/档案缺项/客户停用） |

### 仍存在，需业务或后台侧决策（未擅自改）

1. **员工端不能新增客户**。客户不在档案里就无法开配送单。整改方向：要么后台先建档（当前唯一可行），要么后续在 `pos:order:create` 下开一个受限的"快速建档"（只收姓名/电话/地址），后者涉及客户主数据质量，需单独授权。
2. **`pos:order:create` 只有 SUPER_ADMIN 默认持有**（V59）。店长/店员开单会 403。这是权限配置问题，需在后台「角色管理」给实际收银角色勾上；代码无缺陷。
3. **商品目录无门店维度，但这是对的**（2026-11-08 晚复核纠正）：`product` 是全局主数据，不分门店；按门店隔离的只有库存。库存这条已成立——`inventory` 实测是 `(store_id, product_id) → quantity` 的一行一商品投影（表结构无 `batch_no`），移动端 `/pos/catalog/inventory` 不传 `storeId` 时后端强制取员工本店（`scopedStore`），非管理员传别店直接拒绝，下单扣减用订单门店。
4. **真正不一致的是数量口径，不是门店维度**：后台列表与移动端都读 `inventory.quantity` 投影，而扣减读 `inventory_batch_balance.base_quantity - reserved_base_quantity` 且排除过期批次与停用货位（`InventoryLedgerService.select`）。偏差来源有三：预留、过期批次、停用货位。开发库三者当前均为 0，故实测数字恰好一致（93/60/40），上线后必然分叉。整改方向见 `2026-11-08-库存口径与员工端范围确认及下一步排期.md`。
5. **`validateSaleQuantity` 不查库存**（只校验单位与数量格式），库存不足要到出库 `select()` 才抛"可用库存不足，已排除预留及不可销售批次"。事务会回滚、不会错账，但用户是提交后才看到失败。
6. **客户档案 `phone`/`address` 允许为空**，是后台客户表单没做条件必填。整改方向：后台对参与配送的客户提示补全；本轮不动后台表单。
7. **能力不对称**：后端仍支持赊销与多支付方式，员工端只开现金。属有意收窄，需在对外说明中保持一致口径，避免被理解为"系统不支持"。
