## 为什么修改数据库

现V149问题/entry只表达不可变原话和收据，无法持久识别“已取得执行权、供应商可能收费但结果未知”。因此新增V150，仅给原entry增加8项处理元数据和索引/CHECK；不新建会话/客户/预算表，不修改V149，不回填旧记录或覆盖原body、hash、版本收据。

| 列 | 类型 | 用途 |
|---|---|---|
| assistant_state | VARCHAR(16)，旧记录NULL | QUEUED/RUNNING/COMPLETED/FAILED/UNKNOWN |
| assistant_snapshot | TEXT，应用≤49152 UTF8字节 | 原客户授权纪元、原case/农情版本、原问题/三农情/独立最近补充、执行配置与计价；不可变并纳入原hash |
| assistant_outcome | TEXT，有界JSON | NOT_DISPATCHED/UNKNOWN/STAGED/STALE；草案仅内部未发布 |
| assistant_budget_day | DATE | 上海业务日期，原预占日期不随重试改写 |
| assistant_model_reserved_microusd | BIGINT，非负 | 按配置最坏生成费预占，不是实际扣费 |
| assistant_search_reserved_microusd | BIGINT，非负 | 搜索分项预占，不是实际扣费 |
| assistant_claim_key | CHAR(36)，私有 | 一次执行凭证，不返回客户 |
| assistant_updated_at | DATETIME | 状态推进时间；原entry.created_at不变 |

新增day/case索引；数据库约束只允许真实CUSTOMER的ASSISTANT_REQUEST元数据、有效状态、非负预占、RUNNING/UNKNOWN有凭证。普通历史记录保持NULL。源码最高150；本批只在随机自动测试库执行新增迁移，原开发库/预览服务和此前人工验收库未升级，不能据文件名冒称某运行库已150。

## 事务和请求合同

1. **准备：**实际客户与customer.auth_version重核，原case锁→既有store行锁，真实READ_COMMITTED查本店同日生成/搜索预占次数及金额。先写原entry、不可变快照和预占，再同事务推进case version。确认同意发送最少上下文、原UUID/版本/农情版本必须明确；无配置/零额度/余额不足不落请求或推进版本。
2. **核原号：**原UUID先对完整客户端参数和不可变快照共同摘要；跨问题/动作、改版本/同意字段、篡改快照拒绝。完成请求不因当前配置变化重新报价、调用或改原收据。
3. **唯一派出：**原case锁下QUEUED CAS写入私有claimKey并RUNNING，提交后才在事务外调用内部workflow端口。不同case共用store预算锚，不能同时消费最后一份额度。claim后不持case/store锁等待HTTP。
4. **未知：**RUNNING/UNKNOWN重放和进程重启只返回原状态，查询不出网；同case未决时不接受另一UUID。久未决可显式标UNKNOWN，始终保留生成/搜索最大预占，不凭NETWORK/DEADLINE、异常文本或“没找到回复”推断没收费。
5. **明确未派出：**QUEUED在派出前发现事实、客户纪元、门店、计价执行配置或日期改变，FAILED/NOT_DISPATCHED并释放预占。仅此路径可释放；已取得RUNNING不作费用回退。
6. **晚回写：**同一私有claimKey才可提交处理元数据；当前case/facts/customer/门店仍有效才STAGED，否则STALE且不保存草案。已派出最大预占继续保留。草案不写成门店答复，不变更钱货或服务完成状态。

**计价：**服务器不可变配置的模型、是否搜索、价格版本及费率进快照，输入按32768token上界、输出最高2048计价，用整数/BigInteger向上取整。默认开关关、日次数/金额0；不是用户的付费授权，也不是供应商余额/账单。此层保守记录预占，尚未实现实际分步usage及费率对账，不把预占统计叫实际消费。

## 与既有页面兼容

AI请求仍在原case/entry内，只有处理元数据可推进。原问题/农情及历史收据不可改；独立查询最近客户SUPPLEMENT，不用“前20条没有补充”猜无现场情况。

客户/员工原对话查询均按原已支持类型正向过滤，内部ASSISTANT_REQUEST不会使旧页面拒绝整份详情，也不冒充客户说过的AI答案。后台/员工专业回复与原权限不改；客户仍11页、员工18页，无本批页面或浏览器变更。
