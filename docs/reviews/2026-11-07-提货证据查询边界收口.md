# B3 提货证据查询边界收口验收

日期：2026-11-07
范围：`PickupFulfillmentService` 两处只读 SQL 提取为领域查询端口 + infra 唯一实现。
依据：`docs/reviews/2026-11-04-B3剩余JDBC边界职责核查.md` 中「可提取但留独立子项，
前置条件：SQL 文本逐字一致、preview/confirm 证据链行为不变」。

## 为什么做、更简单的方案

- **问题**：应用主代码仍直接持有 JdbcTemplate 与两段 SQL（基准单位名、出库/退货移动事实 +
  处理中售后派生列），与已收口的 `TransferRecordQuery` / `PickupTaskQuery` /
  `AssignedDeliveryTaskQuery` 模式不一致；应用层也不该依赖 Spring JDBC 类型。
- **更简单的方案**：保留现状。11-04 核查已判断这两处属提货交付资格证据链，收益仅为分层
  纯净，不宜顺手拆；因此本子项单独立项、先建改前基线再动，并锁定「只搬不改」边界。
- **本轮不做**：不为消除 Map 投影而重写 `SELECT m.*` 的 9 个列、不把剩余量计算或交付资格
  判断搬进 infra、不合并 `PickupTaskQuery`（避免制造第三个平行接口或改变查询粒度）。

## 边界与遗留

- 不新增表/字段/迁移；不改任何库存写入、锁、事务连接或提货确认的钱货行为；未改部署与前端。
- `findMovements` 的空 `allocationIds` 短路是新增防御：原调用方 `remainingEvidence` 在
  `allocations.isEmpty()` 时已提前返回，该分支在现有业务路径不可达，仅防止端口被误用时
  生成 `IN ()` 非法 SQL。
- 本轮不是真机、HTTP 全链路或远端 CI 验收；Gitee 仍以本地命令验证为准。
- 应用层 JdbcTemplate 现剩 2 文件：`InventoryLedgerService`（库存账本核心，保留）与
  `JdbcAccessConfig`（Flex 同连接/隔离级别适配，保留），均为 11-04 核查确认的必要保留项。
  至此 B3 无待办代码边界；剩余为 B1 证据驱动评估与 D 组业务决策。
