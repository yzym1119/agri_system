# 专用金有效期 · 设计方案与实施前置确认

日期：2026-11-07
性质：**设计文档，未实施、未新增表/字段、未改 DDL 与生产代码**。
背景：用户 2026-11-07 决定「专用金不取消（保留按商品行限制）、先修发放缺陷、可以加有效期」。
本轮已完成发放缺陷修复（见 `2026-11-07-专用金发放缺陷修复验收.md`），本文解决「有效期怎么做才不会做错账」。

## 一、核心判断：不能只在 `customer_wallet` 加一个 `expire_at`

现有结构是**聚合余额池**：`customer_wallet` 按 `wallet_type=2` 只有一行 `balance`，
四个来源（手动发放、充值赠送、VIP 月度权益、退款原路回退）都往同一个 `balance` 累加，
消费与退款也只改这一个数（`WalletApplicationService` 的 `addSpecialFund` /
`deductSpecialFund` / `refundSpecialFund`）。

在余额池上加单一到期日会产生三个无法回避的错误：

1. **续发即给旧钱延期**：客户 1 月收到 100 元、6 月又收 100 元，若统一 `expire_at` 被刷新，1 月那笔永远不会过期；若不刷新，6 月新发的钱立刻按旧到期日过期。
2. **消费不区分批次**：无法回答「这次扣的是哪一笔、哪一笔该到期作废」，到期时只能整池清零，台账 `wallet_transaction` 无法解释余额变化，财务不可审计。
3. **退款原路回退失去依据**：AGENTS.md 要求专用金退款回 `wallet_type=2`；若原发放批次已过期，退回的资金该算有效、已作废，还是重新起算有效期，单一字段无法表达。

**结论**：要正确表达有效期，必须把「余额」升级为「按批次的可用额」。这与本项目库存「收货批次 + 批次余额 + 追加流水」是同一类事实模型，不是新发明。

## 二、更简单方案对比（AGENTS.md 要求先答「有没有更简单方案」）

| 方案 | 做法 | 代价 / 否决理由 |
|---|---|---|
| **S0 单字段到期日** | `customer_wallet` 加 `expire_at` + 定时清零 | **否决**：上述三个错误，会做错账，且不可逆地抹掉余额来源 |
| **S1 券承接有效期** | 新发放改为发「带有效期的券」，专用金只保留退款沉淀 | **零新表**，但券是整单一次性不找零（`V69`），会失去专用金的部分抵扣能力；且改变资金来源语义，**等于变相取消专用金**，与本次决定冲突。可作为长期演进方向，不用于本次 |
| **S2 批次账（推荐）** | 新增发放批次表，按批次记录可用额与到期日，消费 FEFO、到期核销、退款回退有据 | 需 1~2 张新表 + 支付/退款链路改造 + 定时核销，是独立子项；但语义正确、可审计、不破坏既有契约 |
| **S2-轻量** | 只加 1 张批次表；退款回退统一生成「自退款日起算有效期」的新批次，不追溯原批次 | 少一张表、改动面小；但「退款让已过期的钱复活」需业务明确接受 |

## 三、S2 设计草案

### 3.1 新表（V139，示意 DDL，实施时按现有命名/字符集规范定稿）

```sql
CREATE TABLE special_fund_batch (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  store_id        BIGINT       NULL COMMENT '发放门店，NULL 表示不区分',
  customer_id     BIGINT       NOT NULL,
  source_type     TINYINT      NOT NULL COMMENT '1手动 2充值赠送 3VIP月度 4退款回退',
  source_ref      VARCHAR(64)  NULL COMMENT '来源单号/权益记录，trace 用',
  total_amount    DECIMAL(10,2) NOT NULL,
  remaining_amount DECIMAL(10,2) NOT NULL,
  expire_at       DATETIME     NULL COMMENT 'NULL=永久有效，仅用于存量迁移，不猜历史',
  status          TINYINT      NOT NULL DEFAULT 1 COMMENT '1可用 2用尽 3已过期核销',
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  -- CHECK: remaining_amount >= 0 且 <= total_amount
  KEY idx_customer_expire (customer_id, expire_at, status),
  CONSTRAINT fk_sfb_customer FOREIGN KEY (customer_id) REFERENCES customer(id)
);
```

**迁移方式**：V139 建表 + 为存量 `wallet_type=2 AND balance>0` 的客户各生成一条
`source_type=5(存量迁移)`、`expire_at=NULL` 的批次，`total_amount=remaining_amount=当前余额`。
`NULL` 表示「历史不猜到期日」，符合项目「未知历史不猜值」的既有约定；
新发放一律写明确到期日。**不回改任何历史流水、不删列、不动 `customer_wallet`**。

### 3.2 写入口（4 处，均需同步写批次）

| 入口 | 现状 |
|---|---|
| 手动发放 | `WalletApplicationService.addSpecialFund`（本轮已加金额防线） |
| 充值赠送 | `WalletRechargeService` 直接操作钱包实体 + `recordTransaction` |
| VIP 月度 | `VipLifecycleService` 直接操作钱包实体 + 写流水 |
| 退款回退 | `WalletApplicationService.refundSpecialFund` |

> 注：后三处不走 `addSpecialFund`，实施时必须逐处补齐，不能只改一个方法。这是本次最容易漏的地方。

### 3.3 消费与支付瀑布

- `deductSpecialFund` / `PosOrderCreationService` 的专用金扣减改为 **FEFO（先到期先用）**，按批次扣 `remaining_amount`，写批次消耗明细。
- 支付瀑布的 `specialFundBalance`（`OrderPaymentService.previewPayment:100-106`）改为
  **「未过期批次 remaining 之和」**，再与 `maxSpecialFund`（仍按商品行）取 min。
- 前端 `CheckoutDialog.vue` 的可用额继续由后端报价提供，不自行推算；现有「按商品行上限」保持不变。

### 3.4 退款回退与到期核销

- 退款：优先按原支付消耗的批次回退（需要 S2 完整版的消耗明细表）；S2-轻量则生成新批次。
- 到期：定时扫描 `status=1 AND expire_at<=now()`，把 `remaining_amount` 核销为 0、
  置 `status=3`，同步扣减 `customer_wallet.balance` 并写 `wallet_transaction`（transaction_type=5 扣除），
  **必须幂等**（以批次状态为条件更新，重复执行不二次扣钱）。

### 3.5 影响面（估算，实施时以真实 diff 为准）

新增 1~2 张表 + 1 个 V139 迁移；改 4 个发放入口、2 个扣减入口、1 个退款入口、
支付预览/正式支付、POS 瀑布、前端可用额展示、定时核销任务；
新增批次 FEFO / 到期幂等 / 退款回退 / 存量迁移 / 真实 MySQL 升级测试。
属于**钱货核心链路改造**，应单独一轮实施，不与其它重构混合。

## 四、实施前需要你确认的 5 个语义点

1. **有效期长度**：统一固定天数（建议 180 天 / 365 天），还是按来源/活动可配？
   → 可配需要再加配置字段或沿用 `marketing_recharge_rule` / `marketing_vip_rights`，复杂度上一个台阶。
2. **消费顺序**：FEFO（先用快过期的，对客户有利，推荐）还是按发放先后 FIFO？
3. **过期余额**：直接作废并记台账（推荐），还是转本金/退还客户？作废涉及负债核销口径，需财务确认。
4. **退款回退**：原批次已过期时，是「按退款日重新起算有效期」（S2-轻量）、「直接作废」还是「转本金」？
5. **存量余额**：是否接受「永久有效、不补造到期日」（推荐，不猜历史）？若要给存量统一到期日，需要你给出具体日期。

> 建议默认值（若你认可可直接实施）：**统一 365 天 + FEFO + 过期作废记账 + 退款按新批次重新起算 + 存量永久有效**。
> 这套默认值改动面最小（S2-轻量、1 张新表），且不动现有「按商品行限制」与分账回退契约。
